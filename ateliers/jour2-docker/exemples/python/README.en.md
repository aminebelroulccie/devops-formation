# Python example — FastAPI, venv copied between stages

_English version · la version française est dans [`README.md`](README.md)_

**What this example shows**: multi-stage applied to an interpreted language. The size gain is
modest (the interpreter stays), but the final image contains no pip, no caches and no build
tools: the win is mainly **cleanliness and security**. Same structure as the
`Dockerfile.multistage` of the Formini Tasks running example, with a venv instead of `--prefix`.

```bash
docker build -t formini-hello-python .
docker run --rm -p 8000:8000 formini-hello-python
curl -s localhost:8000/        # {"service":"formini-hello-python","message":"Bonjour Formini",...}
curl -s localhost:8000/health  # {"status":"ok"}
open http://localhost:8000/docs   # interactive docs generated by FastAPI
docker images formini-hello-python
```

## Things to notice

- The venv is created in the build stage and copied as is: `PATH="/venv/bin:$PATH"` is enough
  for `uvicorn` and `python` to resolve to it.
- `PIP_NO_CACHE_DIR=1` keeps the pip cache out of the layer.
- `--workers 2`: uvicorn manages several processes, like gunicorn in the running example.
- Compare with a single-stage `FROM python:3.12` (not slim): `docker images` shows ≈ 1 GB
  versus ≈ 150 MB, and `trivy image` reports dozens more CVEs.

## Exercise

Add a heavy dependency (`pandas==2.2.3`) to `requirements.txt`, rebuild and watch which layer is
rebuilt and how much the image grows. Then remove it: is the previous layer's cache reused?
