Part 1 / 4

Continuous integration and delivery

Why check every commit, and what a pipeline has to do between the code and production.

One-sentence transition: before opening a YAML file, we agree on what a pipeline has to do and why. Ten minutes of concepts, then we move on to the tool.
Before

Integration hell

Everyone in their own branch, for weeks

On merge day, nothing compiles. The tests? We'll run them later. The release build is a two-day ritual, with a single expert able to perform it.

The symptom

"It worked on my machine." Nobody knows which version is in production or how it was built.

The longer you wait to integrate, the more it hurts. The only remedy: integrate all the time, and let a machine check every single time.

Tell the story of release Friday: the six-week branch, the 40 conflicts, the build that only passes on Karim's workstation. Ask who has known a build that only one person knew how to run. Transition: CI is about making that ritual boring, repeatable and instant.
Definitions

CI, CD and… CD

Continuous integration

Every commit is merged early and checked automatically: compilation, lint, tests. Within minutes you know whether you broke something.

Continuous delivery

Every validated version is ready to deploy: image built, tagged, published. Deployment remains a human click.

Continuous deployment

The click disappears: whatever passes the pipeline goes to production on its own. Requires solid tests and monitoring.

Today: continuous integration in the morning, continuous delivery in the afternoon. Continuous deployment comes tomorrow with Kubernetes.

The two "CDs" are often confused. The difference comes down to one question: who presses the button? Continuous delivery = the human decides when; continuous deployment = the pipeline decides. Few teams need continuous deployment from day one.
Why

Two simple ideas

10 min

Fast feedback

A bug found ten minutes after the commit is fixed in ten minutes: the context is still in your head. The same bug found three weeks later costs a day.

1

Small batches

A twenty-line commit that breaks the pipeline is diagnosed at a glance. A two-thousand-line merge is not. CI naturally pushes towards small, frequent changes.

Team rule: a red pipeline on main is the top priority. Nothing else gets pushed until it is green again.

Ten minutes is the classic target for the total duration of a CI pipeline. Beyond that, people stop waiting and pile up commits. Link back to the DORA metrics from day 1: lead time and failure rate depend directly on the speed of feedback.
The stages

The anatomy of a pipeline

Each stage runs only if the previous one succeeded. Fastest first: a ten-second lint saves you from waiting for a three-minute build for nothing.

Walk through the six stages from left to right. Stress the order: cheapest checks first. Publishing happens only on main, not on pull requests, so the registry does not fill up with draft images. The dotted deployment box is for tomorrow.
What each stage checks

Questions, not tools

StageThe questionOur toolTarget time
LintDoes the code follow the team's rules?flake810 s
TestsIs the expected behaviour preserved?pytest1 min
BuildCan we produce an identical artifact every time?docker build2 min
ScanDoes the artifact ship with known vulnerabilities?trivy30 s
PublishIs the artifact findable, versioned, immutable?Gitea registry30 s

Tools change from one project to the next, the questions stay the same. A Java pipeline swaps flake8 for Checkstyle and pytest for JUnit; the structure does not move.

The point of this slide is to separate the notion of a stage from the tools. Ask the room: in your projects, who answers the question "is the artifact findable"? Often nobody. Note the durations: they add up to the ten-minute target.
Part 2 / 4

Gitea Actions

A YAML file in the repository, a runner that listens: the CI/CD engine built into our forge.

Now into the tool. Warn them: the syntax is that of GitHub Actions, so anything they may have seen elsewhere applies. The next slides lead directly into the 10:45 lab.
Anatomy of a workflow

A YAML file in the repository

name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Dependencies
        run: |
          python3 -m venv .venv
          .venv/bin/pip install -q -r requirements-dev.txt
      - name: Lint
        run: .venv/bin/flake8 .
      - name: Tests
        run: .venv/bin/pytest -q
on
When: push, pull request, tag, schedule.
jobs
What: independent units, run in parallel by default.
runs-on
Where: the label of the runner that will pick up the job.
steps
How: commands or actions, in order.

File lives in .gitea/workflows/. Same syntax as GitHub Actions: examples carry over as is.

Read the file top to bottom with the room. Four questions: when, what, where, how. Stress that the workflow is versioned with the code: it evolves in the same pull requests, and it is reviewed like everything else.
The vocabulary

The keywords that show up everywhere

uses
Calls a reusable action: actions/checkout@v4 fetches the code.
run
Runs a shell command. Multi-line with |.
needs
Orders jobs: build waits for test to be green.
if
Condition: gitea.event_name == 'push'.
env
Environment variables, at workflow, job or step level.
secrets
Values encrypted on the Gitea side: ${{ secrets.REGISTRY_TOKEN }}.
matrix
Runs the same job with several values: Python versions, operating systems.
artifacts
Files kept after the job: test report, binary.

The ${{ gitea.sha }}, ${{ gitea.ref_name }}, ${{ gitea.event_name }} context describes the current event. github.* works too, for compatibility.

Do not go through everything: this slide is a reference, we will come back to it during the lab. Above all remember needs, if and secrets, which will be used this afternoon. Mention that the expressions in double curly braces are evaluated by Gitea before execution.
Under the hood

Gitea and act_runner

The runner polls Gitea, never the other way round: it can run behind a firewall, with no open port. One Gitea, as many runners as you like.

The point to get across: Gitea only orchestrates, the runner does the work. The runner runs on your VM, so when a job is slow, it is your VM that is slow. Advantage of polling: no inbound network opening, the runner can be anywhere.
act_runner

Labels: where a job runs

Each runner advertises labels. A job requests a label with runs-on. Gitea matches them.

LabelModeThe job runs…
ubuntu-latest:hosthostdirectly on the VM, with its tools
ubuntu-latest:docker://node:20dockerinside a disposable container

Host mode (our choice)

  • Docker, Python, trivy already there: nothing to install on each job.
  • Fast, easy to debug: commands can be replayed by hand.
  • Less isolated: a job can leave the machine dirty.

Docker mode

  • Clean, reproducible environment on every job.
  • Building an image from inside a container requires Docker-in-Docker.
In training we choose host mode to move fast and see what happens. In production, docker mode is the norm for isolation. Mention that a label can also target a system (windows, arm) or a capability (gpu).
Registration

Connecting a runner to Gitea

# 1. token: Gitea → Site Administration → Actions → Runners
# 2. register the runner with its label
act_runner register --no-interactive \
  --instance http://gitea.formini.local:3000 \
  --token <TOKEN> \
  --name vm-amina \
  --labels ubuntu-latest:host

# 3. run it as a service
sudo systemctl enable --now act_runner
journalctl -u act_runner -f
instance
The Gitea URL, the one you use in the browser.
token
Registration token, global, per organization or per repository.
labels
What this runner can do. Must match runs-on.

Check: Repository → Settings → Actions → Runners. A green dot, otherwise the job will stay "waiting" forever.

The runners are already registered on the VMs by the setup script. Show the list of runners and their labels in the Gitea admin: it is the first place to look when a job does not start. A waiting job with no free runner stays waiting indefinitely.
Reading a run

Where to look when it's red

  1. The repository's Actions tab lists runs per workflow, with the commit and branch that triggered them.
  2. The failed job is marked with a cross. One click opens the steps; only the faulty step is expanded.
  3. The last line of the log almost always says why. Work upwards from there, not from the beginning.
  4. Replay locally the exact command of the step on the VM: same tool, same directory, same result.

A job that is waiting rather than failed is not a bug in the code: it is a missing runner or a label that does not match.

Show a real run in the interface: navigation, expanding steps, searching the log. Distinguish the three states: waiting, running, finished. The classic trap this morning will be the job stuck waiting because the runner went down.

Part 3 / 4

Secrets and security

How a pipeline handles passwords without ever showing them, and what it checks before delivering.

Back from lunch. Ask who still has a red run they do not understand: fix it in front of everyone in two minutes before moving on. Then announce: secrets, scanning, branch protection.
Secrets

Never in the code. Never.

What counts as a secret

  • Access tokens for the registry, the API, the cloud.
  • Database passwords.
  • Private SSH keys, certificates.

What happens otherwise

A committed secret is in the history forever, even after deletion. On a public forge, it is exploited within minutes.

.env
Local only, and in .gitignore from the very first commit.
Gitea
Encrypted secrets, defined per repository or per organization, never readable again.
Logs
Gitea masks the value with *** if it shows up in any output.
Rotation
An exposed secret gets revoked and replaced, it does not get "hidden".
True story to tell: AWS keys pushed to GitHub, a bill of several thousand euros the next morning, bots scan commits continuously. Stress "forever": git rm is not enough, you have to rewrite the history and above all revoke the secret.
Secrets in Gitea

Declare, then use

env:
  REGISTRY: gitea.formini.local:3000

steps:
  - name: Log in to the registry
    run: |
      echo "${{ secrets.REGISTRY_TOKEN }}" \
        | docker login $REGISTRY \
            -u "${{ secrets.REGISTRY_USER }}" \
            --password-stdin
  1. Create a tokenProfile → Settings → Applications, package: write permission.
  2. Declare the secretsRepository → Settings → Actions → Secrets: REGISTRY_USER, REGISTRY_TOKEN.
  3. Read with ${{ secrets.NAME }}The value never appears in the interface or the logs.

--password-stdin keeps the token out of the process list.

Demo: create the token, declare it, launch a run that echoes it to show the asterisks. Then delete that step: we do not leave an echo of a secret lying around, even masked. An organization secret is shared by all the team's repositories, handy for the registry.
Scanning

Three safety nets

Code quality

flake8 catches silly mistakes: unused variable, missing import, dead code. Ten seconds, zero serious false positives.

Dependencies

pip-audit compares requirements.txt against known vulnerability databases. The flaw rarely comes from your code, often from a library.

Image

trivy scans the whole Docker image: base system, packages, Python libraries. It blocks the pipeline if a critical flaw is fixable.

Scanning is only useful if it blocks. A report nobody reads protects against nothing: --exit-code 1 turns the scan into a gate, not an opinion.

Three levels: the code, the dependencies, the image. Ask which level is most often forgotten: the image, because nobody thinks about the base OS. The keyword is block: the scan must have veto power over publication.
Trivy

Scanning an image in practice

# overview, human-readable
trivy image gitea.formini.local:3000/equipe-a/formini-tasks:a1b2c3d

# in the pipeline: block only on fixable critical findings
trivy image \
  --severity CRITICAL \
  --ignore-unfixed \
  --exit-code 1 \
  gitea.formini.local:3000/equipe-a/formini-tasks:a1b2c3d
severity
Levels considered: CRITICAL first, HIGH later.
ignore-unfixed
Ignores flaws with no fix available.
exit-code
Non-zero if a flaw is found: the step fails.

Common remedy: rebuild on an up-to-date base image.

Demo on yesterday's image: show the trivy table, the number of flaws per severity, then the blocking command. Explain ignore-unfixed: without it, the pipeline would be permanently red because of base-system flaws with no fix available.
Branch protection

The pipeline, guardian of main

  1. Repository → Settings → Branches, protect main.
  2. Forbid direct pushes, require one approval.
  3. Require the test status: merging waits for the pipeline.

Combined with yesterday's code review: a human and a machine validate every change.

Show the two PRs side by side. The greyed-out merge button is the whole course made concrete: nobody can bypass the tests, not even the admin. Do the setup live in the branch settings, and note the exact name of the status: CI / test (pull_request), hence the CI / test* pattern.
Part 4 / 4

Delivery strategies

Naming versions, publishing at the right moment, separating environments.

Last theory part, short. The goal is to give the vocabulary of tags and environments before the challenge, which asks for a versioned image to be published.
Naming images

A tag says where the image comes from

TagExampleProduced byUsed for
Short SHA:a1b2c3devery push to mainfinding the exact commit, deploying to test
Semver:v1.4.2a v* Git tagshipped versions, changelog, rollback
latest:latestthe latest build of mainlocal convenience. Never in production.

Immutable

One tag, one image, forever. You never "rewrite" v1.4.2: you publish v1.4.3.

Traceable

From the container in production to the commit: docker inspect → tag → git show a1b2c3d.

The latest trap: two machines pulling latest an hour apart do not have the same image, and nobody knows. Semver: major.minor.patch, incremented according to the nature of the change. Tomorrow, Kubernetes will always deploy a precise tag.
Publishing on a tag

A workflow for releases

name: Release
on:
  push:
    tags: ['v*']

jobs:
  release:
    runs-on: ubuntu-latest
    env:
      REGISTRY: gitea.formini.local:3000
      IMAGE: gitea.formini.local:3000/equipe-a/formini-tasks
      VERSION: ${{ gitea.ref_name }}
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t $IMAGE:$VERSION .
      - run: trivy image --severity CRITICAL --ignore-unfixed
             --exit-code 1 $IMAGE:$VERSION
      - run: echo "${{ secrets.REGISTRY_TOKEN }}" | docker login
             $REGISTRY -u "${{ secrets.REGISTRY_USER }}" --password-stdin
      - run: docker push $IMAGE:$VERSION
git tag -a v1.0.0 -m "First release"
git push origin v1.0.0
tags: v*
Triggers only on a tag that starts with v.
ref_name
The tag name becomes the image tag.

The tag is set by a human: that is the decision to ship.

One workflow per intent: ci.yml checks, release.yml ships. Show that a tag is a named, immutable commit. Shipping takes two commands, and the versioned image is in the registry two minutes later.
Environments

The same image, from test to production

Pull requestlint, tests. Nothing is published.
main:sha image published. Deployed to test.
Tag v*:vX.Y.Z image. Deployed to staging.
Productionthe same :vX.Y.Z image, promoted, not rebuilt.

Build once, deploy everywhere

What changes between environments is the configuration (variables, secrets), never the image. What was tested is exactly what gets shipped.

Promotion

Going to production is not a build: it is pointing the environment at an already validated tag. Rolling back is pointing at the previous one.

The "build once, deploy many" principle. Link to configuration through environment variables seen yesterday with Compose: DATABASE_URL changes, the image does not. Tomorrow with Kubernetes, rolling back will literally mean putting the previous tag back.
Good practices

A pipeline the team loves

  • Fast: under ten minutes, lightweight stages first, independent jobs in parallel.
  • Deterministic: pinned versions in requirements.txt, tagged base image, no implicit "latest version".
  • Readable: a name per step, a job per responsibility, a workflow per intent.
  • Reproducible locally: each step is a command you can type on your own machine.
  • Cache: reuse dependencies from one run to the next (actions/cache, Docker layers).
  • Matrix: test several Python versions with a single declared job.

The pipeline is code: it gets reviewed in pull requests, refactored, and documented. A README that explains how to ship is as important as the code being shipped.

Summary slide before the challenge. Ask the room which practice they miss most in their current projects. Warn them: the challenge asks them to chain build, scan and publication; aim first for a pipeline that works, optimize afterwards.
