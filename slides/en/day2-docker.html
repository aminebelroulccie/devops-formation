Part 1 / 4

Containers and virtual machines

What a container isolates, what it shares, and why it starts in a second.

The problem

"It works on my machine"

An application depends on far more than its code:

  • A precise version of Python, of libraries, of drivers.
  • Configuration files, variables, paths.
  • An operating system with its packages.

Every environment, workstation, test, production, drifts a little. The gaps show up on deployment day.

The container idea: ship the application with its environment, in a single, immutable package that runs identically everywhere.

Analogy: the shipping container. The port does not care about the contents; only the standard shape matters, and the same crane loads everything.

Ask who has already spent a day getting a project handed over by a colleague to run. The container does not remove the complexity, it freezes it in an image everyone shares. Introduce the shipping-container metaphor, we will come back to it for the registry.
Comparison

Virtual machine or container

Key point: a container has no kernel. It is an ordinary, isolated Linux process. Hence the instant start-up and the small size. The trade-off: isolation is weaker than a VM, and a Linux container needs a Linux kernel (on Windows and macOS, Docker Desktop starts a small VM).
Under the hood

An isolated process, nothing more

namespaces
What the process sees. Its own process tree (PID 1), its network interfaces, its mount points, its hostname, its users.
cgroups
What the process may consume. CPU, memory and I/O limits. docker run --memory 256m.
overlayfs
What it reads and writes. The read-only image layers, plus a thin writable layer discarded on removal.
capabilities
What it is allowed to do. A subset of root privileges, reduced by default.
docker run -d --name demo nginx:1.27-alpine
ps -ef | grep nginx          # visible from the host as a normal process
docker exec demo ps -ef      # inside the container: nginx is PID 1
Live demo: start nginx, show ps from the host, then from inside the container. The same process, two points of view. This explains why logs, memory and ports are managed with yesterday's Linux tools.
Part 2 / 4

Images, containers and registries

The vocabulary, the lifecycle, and the commands you type ten times a day.

Vocabulary

Three objects, one flow

DockerfileThe recipe: text, versioned in Git
ImageThe package: immutable, tagged layers
ContainerThe instance: a live process
RegistryThe library: sharing images
build
Dockerfile → image
run
image → container
push / pull
image ↔ registry

An image is to a container what a class is to an object, or an ISO file to a running machine: you can start a hundred containers from the same image.

A public registry: Docker Hub. A private registry: Gitea's, today.

Have them repeat the vocabulary: we build an image, we run a container, we push to a registry. The common mistake is confusing image and container; docker ps -a versus docker images helps fix the distinction.
Lifecycle

Run, observe, enter, stop

docker run -d --name web -p 8080:80 nginx:1.27-alpine
docker ps                      # running containers
docker ps -a                   # including stopped ones
docker logs -f web             # logs (Ctrl-C to exit)
docker exec -it web sh         # a shell inside
docker stop web                # SIGTERM, then SIGKILL after 10 s
docker start web
docker rm -f web               # remove (forces the stop)
-d
Detached: returns the prompt, the container keeps running.
-p 8080:80
Host port 8080 → container port 80.
--name
A readable name rather than an identifier.
-it
Interactive terminal, for exec or run.
--rm
Removes the container when it stops. For experiments.
Walk through the sequence live, open http://localhost:8080 in the VM's browser. Show docker exec to read a config file inside the container. Stress: a stopped container still exists, docker ps -a shows it, docker rm removes it.
Persistence

Disposable, but not its data

The writable layer disappears with the container. Anything that must survive lives outside:

volume
Managed by Docker, named, portable. The default choice for databases.
bind mount
A host folder mounted into the container. Code in development, configuration.
tmpfs
In memory, never on disk. Secrets, caches.
# named volume
docker volume create pgdata
docker run -d --name db \
  -e POSTGRES_PASSWORD=formini \
  -v pgdata:/var/lib/postgresql/data \
  postgres:16-alpine

# bind mount (current folder → /app)
docker run --rm -v "$PWD":/app -w /app python:3.12-slim \
  python -c "print('bonjour')"

docker volume ls
docker volume inspect pgdata
A demo that sticks: start postgres without a volume, create a table, docker rm, start again, the table is gone. Then the same thing with the volume. The afternoon challenge relies on this named volume.
Networking

Containers talk to each other by name

docker network create formini
docker run -d --name db --network formini \
  -e POSTGRES_PASSWORD=formini postgres:16-alpine
docker run --rm -it --network formini postgres:16-alpine \
  psql -h db -U postgres        # "db" is resolved by Docker's DNS

docker network ls
docker network inspect formini
docker port web                 # published ports
  • On the same user-defined network, every container is reachable by its name.
  • The default bridge network does not provide this DNS: always create your own.
  • Only published ports (-p) are visible from the host.

Compose creates this network for you; that is why db works as a hostname in DATABASE_URL.

Anticipate Compose: explain now why this afternoon's connection string will contain "db" and not "localhost". Mistake number one in the challenge: putting localhost in DATABASE_URL, which refers to the web container itself.
Dockerfile

The recipe for an image

FROM python:3.12-slim
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
EXPOSE 5000
CMD ["gunicorn", "-b", "0.0.0.0:5000", "app:create_app()"]
docker build -t formini-tasks:0.1 .
docker run -d -p 5000:5000 formini-tasks:0.1
curl localhost:5000/health
FROM
The starting image. Always a precise version.
WORKDIR
The current folder for the following instructions.
COPY
Files from the build context → image.
RUN
A command executed at build time, creates a layer.
CMD
The command started at run time. Only one.

This version works. This afternoon, we will see why it is slow to rebuild, heavy, and running as root.

This is the Dockerfile the participants write in the guided lab. Deliberately naive: in the afternoon we improve it line by line. Clearly distinguish RUN (at build time) from CMD (at run time), a very frequent confusion.

Part 3 / 4

Writing efficient Dockerfiles

Fast to rebuild, small, secure, and ready for a pipeline.

Layers and cache

The order of instructions changes everything

Each instruction produces a layer. Docker reuses a layer as long as the instruction and the files it touches have not changed. Once a layer is invalidated, all the following ones are too.

Rule: from the most stable to the most volatile. System, then dependencies, then code.

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
Timed demo: edit app.py, rebuild with the naive Dockerfile (pip runs), then with the ordered version (two seconds). That is the difference between a 5-minute and a 30-second pipeline tomorrow.
Build context

Do not copy what does not belong there

.git
.venv
__pycache__
*.pyc
*.db
.env
tests/
.pytest_cache
ateliers/
*.md
  • docker build . sends the whole folder to the engine before the first instruction.
  • A copied .venv or .git: huge image, cache broken on every commit.
  • A copied .env: a secret inside the image, readable by anyone who pulls it.

Check what is in the image: docker run --rm image ls -la /app.

Show the "transferring context" line at the start of a build with and without .dockerignore. The security point about .env prepares day 3: secrets go neither into Git nor into the image, they arrive at run time.
Size and attack surface

Smaller, faster, safer

Base imageSizeUse
python:3.12≈ 1 GBCompilation, debugging
python:3.12-slim≈ 150 MBOur choice
python:3.12-alpine≈ 50 MBBeware of binary wheels
distroless≈ 50 MBNo shell, production

Fewer packages: fewer vulnerabilities to patch, fewer bytes to transfer, faster start-up on Kubernetes.

# stage 1: build the dependencies
FROM python:3.12-slim AS build
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install \
    -r requirements.txt

# stage 2: final image, without pip or build tools
FROM python:3.12-slim
COPY --from=build /install /usr/local
WORKDIR /app
COPY app.py .
COPY static/ static/
Multi-stage is mostly useful for compiled languages (Go, Java) where the final image contains only the binary. Four commented Dockerfiles (Go, Python, React, Rust) live in ateliers/jour2-docker/exemples/: optional demo with build-all.sh if ahead of schedule. For Python, the gain is modest; it is the challenge bonus, we compare sizes with docker images.
Security and operations

The Dockerfile we keep

FROM python:3.12-slim
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app.py .
COPY static/ static/

RUN useradd --create-home --uid 1000 app \
 && chown -R app:app /app
USER app

EXPOSE 5000
HEALTHCHECK --interval=15s --timeout=3s --start-period=10s --retries=3 \
  CMD python -c "import urllib.request;urllib.request.urlopen('http://127.0.0.1:5000/health')"
CMD ["gunicorn", "-b", "0.0.0.0:5000", "--workers", "2", "app:create_app()"]
  • USER: never root in production. A flaw in the app does not give root on the host.
  • HEALTHCHECK: Docker and Compose know whether the app is really ready.
  • ENV: unbuffered logs, visible immediately in docker logs.
  • CMD exec: gunicorn is PID 1 and receives SIGTERM cleanly.
This is the reference solution (ateliers/jour2-docker/solution/Dockerfile). Explain each line added compared with the morning. The exec form of CMD avoids an intermediate shell that would swallow SIGTERM: otherwise docker stop waits 10 seconds and then kills.
Tags

A tag says what, never latest

docker build \
  -t formini-tasks:1.2.0 \
  -t formini-tasks:$(git rev-parse --short HEAD) \
  .
docker images formini-tasks
docker history formini-tasks:1.2.0
docker inspect formini-tasks:1.2.0 | grep -i user
1.2.0
Semantic version: readable, for humans and changelogs.
a1b2c3d
Commit SHA: immutable, exact trace of the code. Tomorrow's pipeline will use it.
latest
A moving alias. Forbidden in production: you never know what is running.

A tag is a label on an image; several tags can point to the same image, without duplicating it.

Anecdote: two servers on "latest" running two different versions because they were pulled on different days. The commit SHA as a tag links the image to the code: essential for the Kubernetes rollback on day 4.
Part 4 / 4

Docker Compose and the registry

Describe several containers in one file, then share the image with the team and the pipeline.

Compose

Several containers, a single file

A real application is the app and its database, its cache, its proxy. Starting them by hand with ten options each is not reproducible.

Compose describes the whole set in compose.yaml, versioned with the code, and drives it with a single command.

docker compose up -d --build
docker compose ps
docker compose logs -f web
docker compose exec db psql -U formini tasks
docker compose down          # keeps the volumes
docker compose down -v       # also deletes the data
Topology of the challenge: two services on a private network, a single published port, a volume for the database. Show that compose down keeps pgdata and that down -v wipes it: this is the classic trap when you want to "start from scratch" without losing your data.
compose.yaml · 1/2

The web service

services:
  web:
    build: .
    image: formini-tasks:dev
    ports: ["8000:5000"]
    environment:
      DATABASE_URL: postgresql://formini:${POSTGRES_PASSWORD}@db:5432/tasks
      APP_VERSION: ${APP_VERSION:-dev}
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped
depends_on
With service_healthy: web waits until Postgres responds.
${VAR}
Read from .env, ignored by Git. We version .env.example.
restart
Restarts after a crash or a reboot of the VM.

The hostname db in the URL is the service name: Compose resolves it on the internal network.

Without the service_healthy condition, web starts before Postgres and crashes with "connection refused": let the participants see it before giving the solution. Show docker compose config, which prints the resolved configuration, passwords included, so never paste it into a ticket.
compose.yaml · 2/2

The db service and its volume

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: formini
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: tasks
    volumes: ["pgdata:/var/lib/postgresql/data"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U formini -d tasks"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  pgdata:
image
No build: an official image, pinned version.
healthcheck
The command that says "ready". It is what depends_on waits for.
volumes
The named volume pgdata, declared at the bottom, survives compose down.

No published port for db: only web reaches it, over the internal network.

Point out the absence of ports on db: it is a good security practice, the database is not exposed on the VM. To access it, go through docker compose exec db psql. The pg_isready healthcheck is provided by the postgres image itself.
Registry

Publishing the image to Gitea

# 1. authenticate (Gitea access token, package scope)
docker login gitea.formini.local:3000 -u formini-a1

# 2. name the image with the registry address
docker tag formini-tasks:dev \
  gitea.formini.local:3000/equipe-a/formini-tasks:0.2.0

# 3. push
docker push gitea.formini.local:3000/equipe-a/formini-tasks:0.2.0

# 4. from another VM: pull and run
docker pull gitea.formini.local:3000/equipe-a/formini-tasks:0.2.0

An image's full name says where it lives:

gitea.formini.local:3000 / equipe-a / formini-tasks : 0.2.0
└── registry ─────────┘   └ org ─┘   └── repo ────┘  └ tag
  • No registry in the name: Docker Hub by default.
  • The Gitea registry is on HTTP: it is declared in the daemon's insecure-registries (done by the install script).
  • Images appear in Gitea → organisation → Packages.
Show the token creation in Gitea: Settings → Applications → Generate token, package read/write scope. The account password works too, but we get into the habit of using a token, tomorrow's pipeline will use one. Push live and open the Packages tab on the projector.

What to remember from day 2

A container is a process
