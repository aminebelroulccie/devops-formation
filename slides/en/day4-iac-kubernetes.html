Before

Infrastructure by hand

The console and the clicks

A server created in twenty clicks, a security group changed "just to test", a rule nobody remembers.

Nobody can reproduce the production environment. The install document is three versions behind.

Drift

Staging and production slowly diverge. A fix works here, not there.

Someone leaves the team, and the knowledge leaves with them. An incident, and you rebuild from memory.

A hand-configured server is a pet: unique, cared for, irreplaceable. We want cattle: numbered, replaceable, recreated identically with one command.

Ask who has already inherited a server whose configuration nobody knew. The "pets vs cattle" metaphor is blunt but it sticks. Key point: the problem is not the AWS console, it is the lack of a trail and of reproducibility.
Infrastructure as Code

Describe, version, review, apply

Reproducible

The same description produces the same infrastructure, today and in six months, here and in another region.

Versioned

In Git, like everything else. Who opened this port, when, why: git log has the answer.

Reviewed

A pull request for an infrastructure change. A colleague reviews, CI checks the plan before applying.

Three tools, three roles

Terraform
Provision: create cloud resources (network, servers, databases).
Ansible
Configure: install and tune what runs on the servers.
Kubernetes
Orchestrate: run the containers, replicate them, update them.
Stress "review": it is the Day 1 DevOps practice applied to infrastructure. A Terraform plan shown in a PR is the equivalent of a code diff. Present the three tools as layers, not competitors.
Part 1 / 4

Terraform

Describe a cloud infrastructure in text files, and let the tool work out what needs to be created, changed or destroyed.

Vocabulary

Five words to understand it all

provider
The plugin that talks to an API. aws, azurerm, google, kubernetes, gitea… hundreds of them.
resource
An object to create. A VPC, an instance, a bucket. Identified by a type and a local name.
variable
An input parameter. The region, the machine size, your name. With a type and a default value.
output
A value exposed after creation. The public IP address, an SSH command ready to copy.
state
Terraform's memory. What it created, with which identifiers. Without it, it recreates everything.

The language is called HCL: blocks, attributes, references between resources. Declarative: you describe the desired state, not the steps.

Draw the parallel with a programming language: provider = library, resource = object, variable = argument, output = return value, state = database. The word "declarative" will come back with Kubernetes this afternoon.
The workflow

Write, plan, apply

The plan is a diff between what the code describes and what the state contains. You always read it before applying. A destroy is a plan that removes everything.

Stress plan: it is the tool's safety net. A plan announcing "1 to destroy" on a database should raise an eyebrow. Show a live init then plan on today's project, and read the + and ~ lines together.
A first file

A server in twenty lines

terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
}

provider "aws" {
  region = var.region
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.micro"
  key_name      = aws_key_pair.formini.key_name
  vpc_security_group_ids = [aws_security_group.web.id]
  subnet_id     = aws_subnet.public.id
  tags = { Name = "formini-${var.owner}" }
}
terraform {}
Required providers, pinned versions.
provider
The region. Credentials come from the environment, never from the code.
resource
A type (aws_instance) and a local name (web).
references
aws_subnet.public.id: the creation order follows from it.
Read the file top to bottom. The takeaway: references between resources build a dependency graph, Terraform creates in the right order and in parallel when possible. Recall yesterday's rule on secrets: never in Git.
Parameterize and expose

Variables in, outputs out

variable "region" {
  type    = string
  default = "eu-west-3"   # Paris
}

variable "owner" {
  type        = string
  description = "Your first name, for the tags"
}

variable "public_key_path" {
  type    = string
  default = "~/.ssh/id_ed25519.pub"
}
output "public_ip" {
  value = aws_instance.web.public_ip
}

output "ssh" {
  value = "ssh ubuntu@${aws_instance.web.public_ip}"
}
terraform apply -var="owner=formini-a1"
# or: a terraform.tfvars file
terraform output public_ip

A variable with no default value is prompted for at run time. Values go in terraform.tfvars, excluded from Git if it contains anything sensitive.

The public key from Day 1 is reused: Terraform sends it to AWS as a key pair. No new key to generate. Show terraform output after the apply: it is the entry point for Ansible right afterwards.
State

The most precious file in the project

terraform.tfstate maps each resource in the code to a real object: instance ID, VPC ID, addresses.

  • Lost: Terraform knows nothing any more, and recreates everything twice over.
  • Shared by e-mail: two people apply, the state diverges.
  • It contains sensitive values in clear text.

As a team: remote state

terraform {
  backend "s3" {
    bucket       = "formini-tfstate"
    key          = "formation/formini-a1.tfstate"
    region       = "eu-west-3"
    use_lockfile = true   # native S3 lock
  }
}

A versioned S3 bucket, a lock against concurrent applies. Never put the state in Git.

Today the state stays local for simplicity. Before terraform destroy, check that the file is still there: without it, cleanup is done by hand in the console.

State is the concept that surprises people: Terraform does not "look at" AWS to know what it created, it reads its file (then refreshes it). Useful anecdote: a tfstate committed to a public Git repo exposes database passwords. The S3 backend is the best practice, mentioned but not practised today.

The commands

Seven commands, one of them mandatory

export AWS_ACCESS_KEY_ID=...        # provided by the trainer
export AWS_SECRET_ACCESS_KEY=...
export AWS_DEFAULT_REGION=eu-west-3

cd terraform
terraform init           # providers, lockfile

init
Once per project.
plan
Touches nothing. Reads like a diff.
apply
Plan, confirmation, creation: two minutes.
destroy
Removes everything the state knows about.

Part 2 / 4

Ansible

The server exists. Now we need to install Docker on it and start the application, without ever logging in by hand.

Principle

Configuring servers without an agent

Ansible connects over SSH from your workstation, runs small Python modules on the target, and leaves. Nothing to install on the server side.

  • The Day 1 SSH key is enough: Ansible uses it.
  • Everything is YAML, readable by a non-developer.
  • Idempotent: replaying a playbook on an already configured server changes nothing.
inventory
The list of machines, by group. [web], [db].
module
An elementary action: apt, copy, service, user.
task
A module call, with a readable name.
playbook
Ordered tasks, applied to a group.
role
A reusable playbook, packaged with its files.
Compare with a shell script: the script says "do this", Ansible says "make sure this is true". Idempotent is the most important word of this part: an apt install already done is skipped, an identical file is not copied again. Direct link to the SSH key created on Day 1.
Inventory and ad hoc commands

Talking to ten servers as if they were one

[web]
15.188.42.17  ansible_user=ubuntu

[web:vars]
ansible_ssh_private_key_file=~/.ssh/id_ed25519
ansible_python_interpreter=/usr/bin/python3
[defaults]
inventory = inventory.ini
host_key_checking = False
# does the target answer?
ansible web -m ping

# one command on the whole group
ansible web -a "uptime"

# a module, with privilege escalation
ansible web -b -m apt -a "name=htop state=present"

# gather facts (OS, IP, CPU…)
ansible web -m setup | head -40

The IP comes from terraform output. Ad hoc commands are for diagnosis; to configure, you write a playbook.

Demo: ping then uptime on the instance created earlier. Show the green "SUCCESS" output and the JSON. host_key_checking set to False is acceptable in training, not in production. Facts are variables available in playbooks.
Playbook

Anatomy of a playbook

- name: Prepare the Formini Tasks server
  hosts: web
  become: true
  tasks:
    - name: Install Docker
      ansible.builtin.apt:
        name: [docker-ce, docker-compose-plugin]
        state: present
        update_cache: true
      notify: Restart Docker
    - name: Copy the application
      ansible.builtin.copy:
        src: ../app/
        dest: /opt/formini-tasks/
  handlers:
    - name: Restart Docker
      ansible.builtin.service:
        name: docker
        state: restarted
hosts
The targeted inventory group.
become
Switch to root (sudo).
state
The desired state, not the action.
notify
A handler, run once at the end, only if something changed.
ansible-playbook playbook.yml
ansible-playbook playbook.yml --check   # dry run
ansible-playbook playbook.yml -t docker # by tag
Read the tasks as sentences. Run the playbook twice in the demo: the first output is yellow (changed), the second green (ok): that is idempotence made visible. The handler only fires if something changed.

Part 3 / 4

Kubernetes

Pods, Deployments and Services: running containers across several machines as if there were only one.

Why

Docker Compose stops at one machine

A server goes down

With Compose, the application goes down with it. Kubernetes restarts the containers elsewhere, on its own.

Traffic doubles

With Compose, you edit a file and pray. Kubernetes goes from 2 to 10 replicas in one command.

A new version

With Compose, a few seconds of downtime. Kubernetes replaces the replicas one by one, with no interruption, and rolls back if it breaks.

Kubernetes is a reconciliation loop: you declare the desired state ("3 replicas of this image"), it constantly compares with reality and corrects the gap. Same logic as Terraform, running continuously.

Go back to the compose.yaml from Day 2: it was perfect for development, insufficient for operations. The word "reconciliation" is the key: link it to the Terraform plan, but executed every second by the cluster itself.
Architecture

A control plane, some nodes

You only ever talk to the API server, with kubectl. The rest is internal machinery. With kind, all of this runs in Docker containers on your VM.

Do not linger: participants will not have to administer the control plane. Two things to remember: kubectl sends YAML objects to the API, and the controllers do the rest. kind = Kubernetes in Docker, each node is a container.
The objects

Deployment, ReplicaSet, Pod, Service

A Pod is the unit of execution: one or more containers, an ephemeral IP. You never create a Pod by hand: the Deployment takes care of it, and the Service makes them reachable by name.

The Pod is mortal: it can disappear at any moment, its IP changes. Hence the Service, which tracks pods by their labels. The ReplicaSet is invisible day to day, but it is what makes the rolling update possible: the Deployment creates a new ReplicaSet and moves the pods over gradually.
The Deployment

Declaring the application

apiVersion: apps/v1
kind: Deployment
metadata:
  name: tasks
  namespace: formini-tasks
spec:
  replicas: 2
  selector:
    matchLabels: { app: tasks }
  template:
    metadata:
      labels: { app: tasks }
    spec:
      containers:
        - name: tasks
          image: gitea.formini.local:3000/equipe-a/formini-tasks:v1.0.0
          ports: [{ containerPort: 5000 }]
          env:
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef: { name: tasks-secret, key: POSTGRES_PASSWORD }
            - name: DATABASE_URL
              value: postgresql://formini:$(POSTGRES_PASSWORD)@postgres:5432/tasks
replicas
How many identical pods.
selector
The pods it owns: those carrying this label.
template
The pod mould: image, ports, variables.
namespace
An isolated space per application.

postgres in the URL is the name of the database Service: DNS is provided.

Three levels of metadata is what loses beginners: the Deployment's, the pod template's, and the selector that links them. Show that the template labels and the selector are identical, otherwise kubectl refuses. The $(VAR) syntax is Kubernetes' native variable expansion.
The StatefulSet

Declaring the database

apiVersion: v1
kind: Service
metadata: { name: postgres, namespace: formini-tasks }
spec:
  clusterIP: None            # headless: DNS points at the pod, not at a virtual IP
  selector: { app: postgres }
---
apiVersion: apps/v1
kind: StatefulSet
metadata: { name: postgres, namespace: formini-tasks }
spec:
  serviceName: postgres      # the Service that gives the pod its identity
  selector: { matchLabels: { app: postgres } }
  template:
    metadata: { labels: { app: postgres } }
    spec:
      containers:
        - { name: postgres, image: postgres:16-alpine,
            volumeMounts: [{ name: data, mountPath: /var/lib/postgresql/data }] }
  volumeClaimTemplates:      # one PVC per pod: data-postgres-0
    - metadata: { name: data }
      spec:
        accessModes: [ReadWriteOnce]
        resources: { requests: { storage: 1Gi } }
Deployment
Interchangeable pods, random names: perfect for the application.
StatefulSet
Pod postgres-0: stable name, stable DNS, its own volume.
PVC per pod
data-postgres-0, created from the template, survives deleting the StatefulSet.
headless
clusterIP: None: no load balancing, one identity per pod.

Rule: anything with state (database, message queue, persistent cache) is declared as a StatefulSet.

Why not a Deployment for the database? Because a Deployment treats its pods as interchangeable: a new name every time, and nothing ties a pod to a specific volume; with two replicas, two postgres processes would write to the same disk. The StatefulSet gives an identity: postgres-0 stays postgres-0, gets its data-postgres-0 PVC back, and pods start and stop in order. Stress the opposite trap: deleting the StatefulSet does not delete the PVC, on purpose, the data survives. In the lab they verify it by deleting the pod. In production you would use an operator (CloudNativePG) or a managed service, but there is a StatefulSet underneath.
Exposing

Three types of Service

ClusterIP

Reachable inside the cluster only, by its DNS name. The default. For the database: the headless variant (clusterIP: None).

postgres:5432

NodePort

Opens a port (30000–32767) on every node. Simple, handy locally with kind.

http://localhost:8080 → 30080

LoadBalancer

Requests a load balancer from the cloud (ELB on AWS). A public IP, ready for production.

EKS, GKE, AKS

apiVersion: v1
kind: Service
metadata: { name: tasks, namespace: formini-tasks }
spec:
  type: NodePort
  selector: { app: tasks }
  ports: [{ port: 80, targetPort: 5000, nodePort: 30080 }]
The Service is an internal load balancer: each request to tasks:80 goes to one of the pods, in turn. With kind we map NodePort 30080 to port 8080 of the VM through the cluster configuration. Mention Ingress as the HTTP layer on top, as a lab bonus.
Configuration

ConfigMap and Secret

apiVersion: v1
kind: Secret
metadata: { name: tasks-secret, namespace: formini-tasks }
type: Opaque
stringData:
  POSTGRES_PASSWORD: change-me
# or, without a file:
kubectl -n formini-tasks create secret generic tasks-secret \
  --from-literal=POSTGRES_PASSWORD='a-real-password'

secret.yaml with a real password does not go in Git. We commit secret.example.yaml, like .env on Day 2.

ConfigMap
Non-sensitive configuration: log level, public URL, config file.
Secret
Passwords, tokens, keys. Base64-encoded, not encrypted by default.
injection
Environment variables (valueFrom) or files mounted into the pod.
Same discipline as with the Gitea secrets yesterday: the value lives outside the repository. Show kubectl get secret -o yaml and decode the base64 to break the illusion of encryption. Production tools (Sealed Secrets, External Secrets, Vault) are not on the syllabus.
Health and resources

Telling Kubernetes how to watch

readinessProbe:
  httpGet: { path: /health, port: 5000 }
  initialDelaySeconds: 5
  periodSeconds: 5
livenessProbe:
  httpGet: { path: /health, port: 5000 }
  initialDelaySeconds: 15
  periodSeconds: 10
resources:
  requests: { cpu: 100m, memory: 128Mi }
  limits:   { cpu: 500m, memory: 256Mi }

/health checks the database: a pod whose database is unreachable is taken out of traffic, not restarted in a loop.

readiness
Ready to serve? No: the Service sends it nothing.
liveness
Still alive? No: the container is restarted.
requests
What the scheduler reserves to place the pod.
limits
The ceiling. Memory exceeded: OOMKilled.
Without a readiness probe, the rolling update sends traffic to pods that are still starting: 502 errors for a few seconds. Without requests, the scheduler piles everything onto one node. The values here are those of the lab solution.

Part 4 / 4

Scaling & rolling updates

What we adopted Kubernetes for: more replicas in one command, a new version with no downtime, a rollback in ten seconds.

Scaling

From two to ten replicas

# manual
kubectl scale deploy/tasks --replicas=4
kubectl get pods -w        # the new pods come up

# or in the YAML, then
kubectl apply -f k8s/app.yaml

# automatic (HPA), with metrics-server
kubectl autoscale deploy/tasks \
  --min=2 --max=10 --cpu-percent=70
kubectl get hpa
  • The Service immediately spreads traffic over the new pods, as soon as their readiness answers.
  • Scaling down is just as easy: surplus pods are stopped gracefully (SIGTERM, grace period).
  • The HorizontalPodAutoscaler adjusts replicas based on CPU or a custom metric. It needs metrics-server and defined requests.

Scaling a stateless application is trivial. The database, however, does not replicate by changing a number: it is a separate topic (StatefulSet, operators, managed service).

Demo: scale to 4 with get pods -w in a second terminal, then generate traffic with a curl loop and show the logs of several pods answering. Make clear that the database stays at a single replica: that is deliberate.
Rolling update

Replacing without downtime

strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1          # extra pods during the switch
    maxUnavailable: 0    # never fewer than replicas
kubectl set image deploy/tasks \
  tasks=gitea.formini.local:3000/equipe-a/formini-tasks:v1.1.0
kubectl rollout status deploy/tasks
kubectl rollout history deploy/tasks
Walk through the timeline from left to right. maxUnavailable: 0 guarantees you never have fewer pods than requested; maxSurge: 1 allows one temporary extra pod. The readiness probe is what makes the switch safe. Show rollout status live with a curl loop that never returns an error.
Rollback

When the new version breaks

# deploy an image that does not exist
kubectl set image deploy/tasks tasks=…:v9.9.9
kubectl get pods
#  tasks-5f…  0/1  ImagePullBackOff
#  tasks-7c…  1/1  Running   ← v1.1.0 still serving

kubectl rollout status deploy/tasks --timeout=60s
# error: deployment "tasks" exceeded its progress deadline

kubectl rollout undo deploy/tasks
kubectl rollout undo deploy/tasks --to-revision=2
  • Kubernetes did not remove the old pods: the new version never passed readiness.
  • The undo reactivates the previous ReplicaSet, the pods come back in seconds.
  • rollout history keeps ten revisions by default. Annotate with --record or a kubernetes.io/change-cause annotation.

This is the Day 1 DORA metric "time to restore", brought down to one command.

Demo the deliberate failure: a non-existent image, then an image that starts but whose /health returns 503. In both cases traffic is never interrupted. Loop back to the DORA metric to show that everything fits together.
