Part 1 / 4

DevOps

Culture, principles and benefits. Why an entire industry changed the way it delivers software.

Before

The wall between Dev and Ops

Developers

Goal: ship features, fast.

Measured on change. "It works on my machine."

Operations

Goal: keep production stable.

Measured on uptime. "No deployments on Fridays."

Two teams, two conflicting goals, and a ticket in between. The result: rare, risky releases and sleepless nights.

Tell the story of a classic failed deployment: the quarterly release, the 40-page installation document, the Ops engineer discovering a missing dependency at 10 pm. Ask the participants whether they have lived through this. The key point: it is not a people problem but an organization and incentives problem.
Definition

DevOps is not a tool, nor a job title

DevOps is a set of practices, tools and a culture that bring development and operations together to deliver more often, faster and more safely.

Culture

Shared responsibility from code all the way to production.

Practices

Continuous integration, infrastructure as code, monitoring.

Tools

Git, Docker, pipelines, Terraform, Kubernetes, Prometheus.

Stress it: you can buy every tool and change nothing. The order matters: culture, then practices, then tools. This week we learn the tools, but each tool serves a practice.
Principles

Five pillars: CALMS

Culture
Collaboration and trust. Fix the system, not the person. Blameless post-mortems.
Automation
Anything repetitive gets scripted. Build, tests, deployment, infrastructure.
Lean
Small batches, continuous flow. A small change is easy to test, deploy and roll back.
Measurement
Measure to decide. Lead time, failure rate, time to recover.
Sharing
Knowledge flows. Documentation, code reviews, demos.
CALMS is the model from Jez Humble and John Willis. Tie it to the week: Automation = days 2 to 4, Measurement = day 5, Sharing = today's pull requests.
The cycle

A loop, not a line

PlanRequirements, tickets
CodeGit, review
BuildCompilation, image
TestUnit, security
ReleaseVersion, registry
DeployKubernetes, IaC
OperateRunning it
MonitorMetrics, alerts

What we observe in production feeds the next planning round. The full cycle can take an hour, not a quarter.

This week: Code (D1) → Build (D2) → Test and Release (D3) → Deploy (D4) → Monitor (D5).

The famous "infinity" symbol. Every step will be automated this week. Ask the question: how long does it take today, where you work, between a commit and its release to production?
Measurable benefits

The four DORA metrics

↑

Deployment frequency

On demand, several times a day for the best teams.

↓

Lead time for changes

From commit to production: less than a day.

↓

Change failure rate

Share of deployments that cause an incident.

↓

Time to restore

How long it takes to get back to normal service after an incident.

Speed and stability improve together: the teams that deploy most often are also the ones that break things the least.

Source: the annual "State of DevOps" reports from DORA (Google). The counter-intuitive message: speed is not the enemy of stability. Small, frequent changes are less risky than big releases.

Part 2 / 4

Linux essentials

Files, permissions, processes and SSH: the foundation of everything that follows.

Finding your way

The layout of a server

/etc
System and service configuration (sshd_config, hosts).
/var/log
Logs. The first place to look when something breaks.
/home
User home directories. ~ is yours.
/opt
Third-party software installed by hand (Gitea, runners…).
/var/lib
Service data: Docker, databases.
/tmp
Temporary files, cleared on reboot.
pwd                 # where am I?
ls -la /etc/ssh     # list, with details and hidden files
cd /var/log && ls
tail -f syslog      # follow a log live
less auth.log       # read page by page (q to quit)
find / -name "*.conf" 2>/dev/null | head
du -sh /var/lib/docker
Do the demo live on the trainer VM. Stress tail -f and less: the two commands we will use every day to read logs. Remind them that "everything is a file" on Linux.
Permissions

Who can do what on a file

-rwxr-x---  1 devops  docker   512  deploy.sh
 │││ │││ │││     │       │
 │└┴─┴┴┴─┴┴┘     │       └── group
 │  u   g   o    └── owner
 └── type (- file, d directory, l link)
LetterValueFileDirectory
r4readlist
w2modifycreate / delete
x1executetraverse
chmod u+x deploy.sh      # make executable
chmod 750 deploy.sh      # rwx r-x ---
chmod 600 ~/.ssh/id_ed25519   # private key: me only
chown devops:docker deploy.sh
sudo usermod -aG docker devops  # add to a group
id devops                # check its groups

Classic mistake: a private SSH key readable by everyone is rejected by the SSH client. chmod 600 is mandatory.

Have them work out 750 and 644 out loud. Show the "UNPROTECTED PRIVATE KEY FILE" error live if possible: it is the number one failure in the SSH lab.
Processes and services

What is running, and how to control it

Processes

ps aux | grep gitea     # find a process
top                     # live load (q to quit)
htop                    # the readable version
kill -15 1234           # ask it to stop
kill -9 1234            # force it (last resort)
ss -tlnp                # listening ports

Services (systemd)

systemctl status docker
sudo systemctl restart ssh
sudo systemctl enable --now docker  # start now + at boot
journalctl -u docker -f             # service logs
journalctl --since "10 min ago"

Reflex to build: a service is not responding → systemctl status, then journalctl -u, then ss -tlnp to check the port.

Demo: stop Docker, observe the error, restart it, read journalctl. This three-command diagnostic reflex will serve all week long.
SSH

Accessing a server without a password

A key pair: the private key stays on your workstation, the public key is copied to the server in ~/.ssh/authorized_keys.

  • No password to remember or to guess.
  • Revocable: delete one line.
  • Essential for automation: Ansible, pipelines, Git.
# 1. generate the key pair
ssh-keygen -t ed25519 -C "prenom@formini"

# 2. send the public key to the server
ssh-copy-id devops@192.168.10.21

# 3. connect
ssh devops@192.168.10.21

# 4. make it simpler: ~/.ssh/config
Host vm
  HostName 192.168.10.21
  User devops
  IdentityFile ~/.ssh/id_ed25519
Draw it on the board: workstation → server, private / public key, padlock / key. Explain that once the key is in place, we disable password authentication on the server side. That will be the lab.
Guided lab · 10:45 – 12:00

A Linux server reachable over SSH

  1. Create the working user devops on your VM, with sudo rights.
  2. Generate a key on the Formini workstation, copy it with ssh-copy-id.
  3. Harden the server: disable password and root login in sshd_config.
  4. Verify from a second window before closing the first one.
  5. Authorize a colleague: add their public key on your VM, and vice versa.

Lab sheet: ateliers/jour1-linux-git/README.en.md

Always keep one session open while you change the SSH configuration. If you lock yourself out, the Formini console remains your emergency exit.

Bonus: install fail2ban, change the listening port, read the login attempts in /var/log/auth.log.

Walk around the room. Frequent failures: permissions on .ssh (700) and authorized_keys (600), forgetting "systemctl restart ssh", typo in sshd_config (test with sshd -t before restarting). The fastest ones do the bonus.
Part 3 / 4

Git

Commits, branches, merges and conflicts. The project's memory and the team's common language.

Mental model

Three areas, one history

A commit is a complete snapshot of the project, identified by a hash (SHA) and linked to its parent. Nothing is ever overwritten: we add snapshots.

The three-area model explains 90% of the confusion. Staging lets you compose a clean commit out of messy work. Show git status between each step.
Everyday commands

A first repository, a first commit

git config --global user.name  "Amina Ben Salah"
git config --global user.email "amina@formini.tn"
git config --global init.defaultBranch main

mkdir formini-tasks && cd formini-tasks
git init
echo "# Formini Tasks" > README.md
git status                 # untracked file
git add README.md
git commit -m "docs: add the README"
git log --oneline --graph
status
The state of the three areas. Type it constantly.
diff
What changed. --staged for the index.
log
The history. --oneline --graph --all for the big picture.
restore
Undo an uncommitted change.
.gitignore
What Git must never track: secrets, .env, binaries.
Live demo. Make a second commit, show git diff before and after add. Show a .gitignore with .env in it: we will come back to it on day 3 with secrets.
Branches

Working in parallel without getting in each other's way

git switch -c feature/login   # create + switch
git branch                    # list
# ... commits ...
git switch main
git merge feature/login
git branch -d feature/login   # clean up

A branch is just a pointer to a commit. Creating one costs nothing. One per task, short-lived.

Metaphor: a branch is a sticky note stuck on a commit. Draw on the board how the pointer moves with each commit. Naming convention: feature/, fix/, chore/.
Merges

Three ways to bring two branches together

Fast-forward

main has not moved: Git simply advances the pointer. Linear history, no merge commit.

Merge commit

Both branches have moved on: Git creates a commit with two parents. Faithful to what really happened, but the graph gets more complex.

Rebase

Replays your commits on top of main. Clean, linear history. Never on a shared branch.

git switch feature/login && git rebase main     # bring my branch up to date cleanly
git switch main && git merge --no-ff feature/login   # force a merge commit (trace of the PR)
Golden rule to write on the board: rebase your local branches, merge into main. Never rewrite the history of a branch that someone else has already pulled.
Conflicts

When two people change the same line

def greet():
<<<<<<< HEAD
    return "Bonjour Formini"
=======
    return "Salut l'équipe"
>>>>>>> feature/greeting

Between <<<<<<< and =======: your version. Between ======= and >>>>>>>: the merged branch's version.

  1. Read git status: the list of conflicting files.
  2. Edit the file, keep the right version (or a combination), remove the markers.
  3. Mark as resolved with git add app.py.
  4. Finish: git commit (merge) or git rebase --continue.

Lost? git merge --abort puts everything back as it was.

A conflict is not an error: it is Git asking for a human decision. Show the resolution in VS Code ("Accept current / incoming / both" buttons). The afternoon lab triggers one on purpose.
Remote repository

Syncing with Gitea

# link the local repository to the server
git remote add origin \
  http://gitea.formini.local:3000/equipe-a/formini-tasks.git
git push -u origin main

# fetch the others' work
git fetch            # downloads without touching my files
git pull --rebase    # fetch + rebase my branch

# clone an existing project
git clone http://gitea.formini.local:3000/equipe-a/formini-tasks.git
origin
Default name of the remote repository. There can be several.
push
Sends my commits. Rejected if the remote has moved on: pull first.
fetch
Downloads the remote state into origin/main without merging anything.
pull
fetch + merge (or rebase).

Gitea is a lightweight, self-hosted Git forge, compatible with GitHub workflows. It will also serve as the image registry (D2) and the CI engine (D3).

Show the Gitea interface: creating an "equipe-a" organization, a repository, the clone button. Explain why we use Gitea rather than GitHub: everything runs locally, on the Formini machines, and we control every piece of it.
Part 4 / 4

Teamwork on Gitea

Pull requests, code review and conventions: how a team keeps its main branch healthy at all times.

The workflow

One branch, one pull request, one review

1 · TicketA clear, small task
2 · Branchfeature/… from main
3 · CommitsSmall, well named, pushed
4 · Pull requestDescription, context, screenshots
5 · ReviewA colleague reads, comments, approves
6 · MergeInto main, branch deleted

Why go through a PR

  • Four eyes are better than two: fewer bugs, more sharing.
  • It is the anchor point for CI: tests run before the merge.
  • A readable trace: why this change, discussed by whom.

Protecting main

  • No direct pushes.
  • At least one approval.
  • Green CI status required (day 3).
Demo in Gitea: Settings → Branches → protection for main. Then a complete PR live, with a volunteer participant as reviewer.
Code review

Reviewing to help, not to judge

A good pull request

  • Small: under 300 lines, a single intention.
  • A title that says what, a description that says why.
  • How to test it, and what is not covered.
  • The author has re-read their own diff before requesting review.

A good review

  • Same day: a PR that waits ages badly.
  • Questions rather than orders: "What if we renamed…?"
  • Distinguish blocking / suggestion / detail (nit).
  • Approve explicitly when it is good.

The reviewer first seeks to understand, then to check: readability, tests, security, side effects. Style is the linter's job, not a human's.

Share an anecdote about a helpful review or a toxic one. Stress the written tone: without intonation, a curt remark hurts. Review comments in Gitea can be attached to a specific line.
Conventions

Commit messages you can actually read

<type>(<scope>): <summary in the imperative>

feat(api): add task deletion
fix(db): fix connection timeout
docs: clarify prerequisites in the README
test(api): cover the missing-task case
chore(ci): update the base image
refactor(models): extract validation
feat
New user-visible feature.
fix
Bug fix.
docs / test
Documentation, tests only.
chore
Maintenance, tooling, dependencies.
refactor
Restructuring with no change in behavior.

The summary fits in 50 characters; the body, if there is one, explains the why. These conventions make it possible to generate a changelog automatically.

Show an unreadable git log ("fix", "wip", "it works") next to a conventional one. The team picks a convention and sticks to it; which one does not matter, consistency is what counts.
Self-paced challenge · 14:00 – 15:30 · teams of three

Three branches, one clean merge

  1. Initialize the formini-tasks repository in the team's Gitea organization, protect main.
  2. One branch each: an API route, a test, the README.
  3. Pull request + review: review someone else's PR, request a change, approve.
  4. Trigger a conflict on the same line of the README, resolve it with a rebase, merge.
  5. Deliver: three contributions in main, a readable history, no dead branches.

Lab sheet: ateliers/jour1-linux-git/README.en.md, part 2

Success criteria

  • Three merged PRs with at least one comment each.
  • A readable, conventional git log --oneline --graph.
  • One conflict resolved with no lost content.

Bonus: tag v0.1.0, a CODEOWNERS file, a PR template in .gitea/.

Form the teams now (they stay the same all week for the final project). Visit each team at the moment of the conflict: that is when the questions come. Around 15:15, ask one team to show its graph on the projector.
