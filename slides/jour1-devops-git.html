Partie 1 / 4

Le DevOps

Culture, principes et bénéfices. Pourquoi une industrie entière a changé sa façon de livrer du logiciel.

Avant

Le mur entre Dev et Ops

Les développeurs

Objectif : livrer des fonctionnalités, vite.

Mesurés sur le changement. « Ça marche sur ma machine. »

Les opérations

Objectif : garder la production stable.

Mesurés sur la disponibilité. « Pas de mise en prod le vendredi. »

Deux équipes, deux objectifs contradictoires, et un ticket entre les deux. Résultat : des livraisons rares, risquées, et des nuits blanches.

Raconter un déploiement raté classique : la release trimestrielle, le document d'installation de 40 pages, l'Ops qui découvre une dépendance manquante à 22h. Demander aux participants s'ils ont vécu ça. Le point clé : ce n'est pas un problème de personnes mais d'organisation et d'incitations.
Définition

Le DevOps n'est pas un outil, ni un poste

Le DevOps est un ensemble de pratiques, d'outils et une culture qui réunissent développement et exploitation pour livrer plus souvent, plus vite et plus sûrement.

Culture

Responsabilité partagée du code jusqu'à la production.

Pratiques

Intégration continue, infrastructure as code, supervision.

Outils

Git, Docker, pipelines, Terraform, Kubernetes, Prometheus.

Insister : on peut acheter tous les outils et ne rien changer. L'ordre compte : culture, puis pratiques, puis outils. Cette semaine on apprend les outils, mais chaque outil sert une pratique.
Principes

Cinq piliers : CALMS

Culture
Collaboration et confiance. On corrige le système, pas la personne. Post-mortems sans blâme.
Automation
Tout ce qui est répétitif est scripté. Build, tests, déploiement, infrastructure.
Lean
Petits lots, flux continu. Un petit changement est facile à tester, à déployer, à annuler.
Measurement
On mesure pour décider. Temps de livraison, taux d'échec, temps de rétablissement.
Sharing
Le savoir circule. Documentation, revues de code, démonstrations.
CALMS est le modèle de Jez Humble et John Willis. Faire le lien avec la semaine : Automation = jours 2 à 4, Measurement = jour 5, Sharing = les pull requests d'aujourd'hui.
Le cycle

Une boucle, pas une ligne

PlanBesoins, tickets
CodeGit, revue
BuildCompilation, image
TestUnitaires, sécurité
ReleaseVersion, registre
DeployKubernetes, IaC
OperateExploitation
MonitorMétriques, alertes

Ce que l'on observe en production nourrit la planification suivante. Le cycle complet peut durer une heure, pas un trimestre.

Cette semaine : Code (J1) → Build (J2) → Test et Release (J3) → Deploy (J4) → Monitor (J5).

Le fameux symbole « infini ». Chaque étape sera automatisée cette semaine. Poser la question : combien de temps entre un commit et sa mise en production chez vous aujourd'hui ?
Bénéfices mesurables

Les quatre métriques DORA

↑

Fréquence de déploiement

À la demande, plusieurs fois par jour pour les meilleures équipes.

↓

Délai de livraison

Du commit à la production : moins d'un jour.

↓

Taux d'échec

Part des déploiements qui provoquent un incident.

↓

Temps de rétablissement

Durée pour revenir à un service normal après incident.

Vitesse et stabilité progressent ensemble : les équipes qui déploient le plus souvent sont aussi celles qui cassent le moins.

Source : rapports annuels « State of DevOps » de DORA (Google). Le message contre-intuitif : la vitesse n'est pas l'ennemie de la stabilité. Les petits changements fréquents sont moins risqués que les grosses releases.

Partie 2 / 4

Linux essentiel

Fichiers, permissions, processus et SSH : le socle de tout ce qui suit.

Se repérer

L'arborescence d'un serveur

/etc
Configuration du système et des services (sshd_config, hosts).
/var/log
Journaux. Premier endroit où regarder quand ça casse.
/home
Répertoires des utilisateurs. ~ est le vôtre.
/opt
Logiciels tiers installés à la main (Gitea, runners…).
/var/lib
Données des services : Docker, bases de données.
/tmp
Fichiers temporaires, vidés au redémarrage.
pwd                 # où suis-je ?
ls -la /etc/ssh     # lister, détails, fichiers cachés
cd /var/log && ls
tail -f syslog      # suivre un journal en direct
less auth.log       # lire page par page (q pour sortir)
find / -name "*.conf" 2>/dev/null | head
du -sh /var/lib/docker
Faire la démo en direct sur la VM formateur. Insister sur tail -f et less : les deux commandes que l'on utilisera tous les jours pour lire des journaux. Rappeler que « tout est fichier » sous Linux.
Permissions

Qui peut faire quoi sur un fichier

-rwxr-x---  1 devops  docker   512  deploy.sh
 │││ │││ │││     │       │
 │└┴─┴┴┴─┴┴┘     │       └── groupe
 │  u   g   o    └── propriétaire
 └── type (- fichier, d dossier, l lien)
LettreValeurFichierDossier
r4lirelister
w2modifiercréer / supprimer
x1exécutertraverser
chmod u+x deploy.sh      # rendre exécutable
chmod 750 deploy.sh      # rwx r-x ---
chmod 600 ~/.ssh/id_ed25519   # clé privée : moi seul
chown devops:docker deploy.sh
sudo usermod -aG docker devops  # ajouter à un groupe
id devops                # vérifier ses groupes

Erreur classique : une clé SSH privée lisible par tout le monde est refusée par le client SSH. chmod 600 est obligatoire.

Faire calculer 750 et 644 à voix haute. Montrer l'erreur « UNPROTECTED PRIVATE KEY FILE » en direct si possible : c'est la panne numéro un de l'atelier SSH.
Processus et services

Ce qui tourne, et comment le piloter

Processus

ps aux | grep gitea     # trouver un processus
top                     # charge en direct (q pour sortir)
htop                    # version lisible
kill -15 1234           # demander l'arrêt
kill -9 1234            # forcer (dernier recours)
ss -tlnp                # ports en écoute

Services (systemd)

systemctl status docker
sudo systemctl restart ssh
sudo systemctl enable --now docker  # démarrer + au boot
journalctl -u docker -f             # journaux du service
journalctl --since "10 min ago"

Réflexe à prendre : un service ne répond pas → systemctl status, puis journalctl -u, puis ss -tlnp pour vérifier le port.

Démo : arrêter Docker, constater l'erreur, relancer, lire journalctl. Ce réflexe de diagnostic en trois commandes servira toute la semaine.
SSH

Accéder à un serveur sans mot de passe

Une paire de clés : la privée reste sur votre poste, la publique est copiée sur le serveur dans ~/.ssh/authorized_keys.

  • Pas de mot de passe à retenir ni à deviner.
  • Révocable : on supprime une ligne.
  • Indispensable pour l'automatisation : Ansible, pipelines, Git.
# 1. générer la paire de clés
ssh-keygen -t ed25519 -C "prenom@formini"

# 2. envoyer la clé publique sur le serveur
ssh-copy-id devops@192.168.10.21

# 3. se connecter
ssh devops@192.168.10.21

# 4. simplifier : ~/.ssh/config
Host vm
  HostName 192.168.10.21
  User devops
  IdentityFile ~/.ssh/id_ed25519
Dessiner au tableau : poste → serveur, clé privée / publique, cadenas / clé. Expliquer qu'une fois la clé en place, on désactive l'authentification par mot de passe côté serveur. Ce sera l'atelier.
Atelier guidé · 10:45 – 12:00

Un serveur Linux accessible en SSH

  1. Créer l'utilisateur de travail devops sur votre VM, avec droits sudo.
  2. Générer une clé sur le poste Formini, la copier avec ssh-copy-id.
  3. Durcir le serveur : désactiver mot de passe et connexion root dans sshd_config.
  4. Vérifier depuis une deuxième fenêtre avant de fermer la première.
  5. Autoriser un collègue : ajouter sa clé publique sur votre VM, et réciproquement.

Fiche atelier : ateliers/jour1-linux-git/README.md

Gardez toujours une session ouverte pendant que vous modifiez la configuration SSH. Si vous vous enfermez dehors, la console Formini reste votre issue de secours.

Bonus : installer fail2ban, changer le port d'écoute, lire les tentatives dans /var/log/auth.log.

Circuler dans la salle. Pannes fréquentes : permissions du .ssh (700) et de authorized_keys (600), oubli de « systemctl restart ssh », faute de frappe dans sshd_config (tester avec sshd -t avant de redémarrer). Les plus rapides font le bonus.
Partie 3 / 4

Git

Commits, branches, fusions et conflits. La mémoire du projet et le langage commun de l'équipe.

Modèle mental

Trois zones, un historique

Un commit est une photographie complète du projet, identifiée par une empreinte (SHA), reliée à son parent. Rien n'est jamais écrasé : on ajoute des photos.

Le modèle en trois zones explique 90 % des confusions. Le staging permet de composer un commit propre à partir d'un travail en vrac. Montrer git status entre chaque étape.
Les commandes du quotidien

Un premier dépôt, un premier commit

git config --global user.name  "Amina Ben Salah"
git config --global user.email "amina@formini.tn"
git config --global init.defaultBranch main

mkdir formini-tasks && cd formini-tasks
git init
echo "# Formini Tasks" > README.md
git status                 # fichier non suivi
git add README.md
git commit -m "docs: ajoute le README"
git log --oneline --graph
status
L'état des trois zones. À taper sans arrêt.
diff
Ce qui a changé. --staged pour l'index.
log
L'historique. --oneline --graph --all pour la vue d'ensemble.
restore
Annuler une modification non commitée.
.gitignore
Ce que Git ne doit jamais suivre : secrets, .env, binaires.
Démo en direct. Faire un deuxième commit, montrer git diff avant et après add. Montrer un .gitignore avec .env dedans : on y reviendra au jour 3 avec les secrets.
Branches

Travailler en parallèle sans se gêner

git switch -c feature/login   # créer + basculer
git branch                    # lister
# ... commits ...
git switch main
git merge feature/login
git branch -d feature/login   # nettoyer

Une branche n'est qu'un pointeur vers un commit. En créer une coûte zéro. Une par tâche, courte durée de vie.

Métaphore : une branche est un post-it collé sur un commit. Dessiner au tableau le déplacement du pointeur à chaque commit. Convention de nommage : feature/, fix/, chore/.
Fusions

Trois façons de réunir deux branches

Fast-forward

main n'a pas bougé : Git avance simplement le pointeur. Historique linéaire, aucun commit de fusion.

Commit de fusion

Les deux branches ont avancé : Git crée un commit à deux parents. Fidèle à l'histoire réelle, mais le graphe se complique.

Rebase

Rejoue vos commits par-dessus main. Historique propre et linéaire. Jamais sur une branche partagée.

git switch feature/login && git rebase main     # mettre à jour ma branche proprement
git switch main && git merge --no-ff feature/login   # forcer un commit de fusion (trace de la PR)
Règle d'or à écrire au tableau : on rebase ses branches locales, on merge dans main. Ne jamais réécrire l'historique d'une branche que quelqu'un d'autre a récupérée.
Conflits

Quand deux personnes modifient la même ligne

def greet():
<<<<<<< HEAD
    return "Bonjour Formini"
=======
    return "Salut l'équipe"
>>>>>>> feature/greeting

Entre <<<<<<< et ======= : votre version. Entre ======= et >>>>>>> : celle de la branche fusionnée.

  1. Lire git status : la liste des fichiers en conflit.
  2. Éditer le fichier, garder la bonne version (ou une combinaison), supprimer les marqueurs.
  3. Marquer résolu avec git add app.py.
  4. Terminer : git commit (merge) ou git rebase --continue.

Perdu ? git merge --abort remet tout comme avant.

Un conflit n'est pas une erreur : c'est Git qui demande un arbitrage humain. Montrer la résolution dans VS Code (boutons « Accept current / incoming / both »). L'atelier de l'après-midi en provoque un volontairement.
Dépôt distant

Synchroniser avec Gitea

# lier le dépôt local au serveur
git remote add origin \
  http://gitea.formini.local:3000/equipe-a/formini-tasks.git
git push -u origin main

# récupérer le travail des autres
git fetch            # télécharge sans toucher à mes fichiers
git pull --rebase    # fetch + rebase de ma branche

# cloner un projet existant
git clone http://gitea.formini.local:3000/equipe-a/formini-tasks.git
origin
Nom par défaut du dépôt distant. Il peut y en avoir plusieurs.
push
Envoie mes commits. Refusé si le distant a avancé : il faut d'abord pull.
fetch
Télécharge l'état distant dans origin/main sans rien fusionner.
pull
fetch + merge (ou rebase).

Gitea est un forge Git auto-hébergée, légère, compatible avec les workflows GitHub. Elle fera aussi office de registre d'images (J2) et de moteur de CI (J3).

Montrer l'interface Gitea : création d'une organisation « equipe-a », d'un dépôt, le bouton clone. Expliquer pourquoi on utilise Gitea plutôt que GitHub : tout tourne en local, sur les machines Formini, et on en contrôle chaque pièce.
Partie 4 / 4

Travail en équipe sur Gitea

Pull requests, revue de code et conventions : comment une équipe garde une branche principale toujours saine.

Le flux de travail

Une branche, une pull request, une revue

1 · TicketUne tâche claire et petite
2 · Branchefeature/… depuis main
3 · CommitsPetits, nommés, poussés
4 · Pull requestDescription, contexte, captures
5 · RevueUn collègue lit, commente, approuve
6 · MergeDans main, branche supprimée

Pourquoi passer par une PR

  • Quatre yeux valent mieux que deux : moins de bugs, plus de partage.
  • C'est le point d'ancrage de la CI : les tests tournent avant la fusion.
  • Une trace lisible : pourquoi ce changement, discuté par qui.

Protéger main

  • Pas de push direct.
  • Au moins une approbation.
  • Statut CI vert obligatoire (jour 3).
Démo dans Gitea : Settings → Branches → protection de main. Puis une PR complète en direct avec un participant volontaire comme relecteur.
Revue de code

Relire pour aider, pas pour juger

Une bonne pull request

  • Petite : moins de 300 lignes, une seule intention.
  • Un titre qui dit quoi, une description qui dit pourquoi.
  • Comment la tester, et ce qui n'est pas couvert.
  • L'auteur a relu son propre diff avant de demander la revue.

Une bonne revue

  • Dans la journée : une PR qui attend vieillit mal.
  • Questions plutôt qu'ordres : « Et si on renommait… ? »
  • Distinguer bloquant / suggestion / détail (nit).
  • Approuver explicitement quand c'est bon.

Le relecteur cherche d'abord à comprendre, puis à vérifier : lisibilité, tests, sécurité, effets de bord. Le style, c'est le travail du linter, pas de l'humain.

Partager une anecdote de revue utile ou de revue toxique. Insister sur le ton écrit : sans intonation, une remarque sèche blesse. Les commentaires de revue dans Gitea peuvent être attachés à une ligne précise.
Conventions

Des messages de commit que l'on peut lire

<type>(<portée>): <résumé à l'impératif>

feat(api): ajoute la suppression d'une tâche
fix(db): corrige le timeout de connexion
docs: précise les prérequis dans le README
test(api): couvre le cas d'une tâche inexistante
chore(ci): met à jour l'image de base
refactor(models): extrait la validation
feat
Nouvelle fonctionnalité visible.
fix
Correction d'un bug.
docs / test
Documentation, tests seulement.
chore
Maintenance, outillage, dépendances.
refactor
Restructuration sans changement de comportement.

Le résumé tient en 50 caractères ; le corps, s'il existe, explique le pourquoi. Ces conventions permettent de générer un changelog automatiquement.

Montrer un git log illisible (« fix », « wip », « ça marche ») face à un log conventionnel. L'équipe choisit une convention et s'y tient ; peu importe laquelle, l'important est la constance.
Défi en autonomie · 14:00 – 15:30 · par équipe de trois

Trois branches, une fusion propre

  1. Initialiser le dépôt formini-tasks dans l'organisation Gitea de l'équipe, protéger main.
  2. Chacun sa branche : une route API, un test, le README.
  3. Pull request + revue : relire la PR d'un autre, demander une modification, approuver.
  4. Provoquer un conflit sur la même ligne du README, le résoudre en rebase, fusionner.
  5. Livrer : trois contributions dans main, historique lisible, aucune branche morte.

Fiche : ateliers/jour1-linux-git/README.md, partie 2

Critères de réussite

  • Trois PR fusionnées avec au moins un commentaire chacune.
  • git log --oneline --graph lisible et conventionnel.
  • Un conflit résolu sans perte de contenu.

Bonus : tag v0.1.0, fichier CODEOWNERS, modèle de PR dans .gitea/.

Former les équipes maintenant (elles restent les mêmes toute la semaine pour le projet final). Passer voir chaque équipe au moment du conflit : c'est là que les questions arrivent. Vers 15:15, demander à une équipe de montrer son graphe au projecteur.
