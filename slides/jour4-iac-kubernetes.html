Avant

L'infrastructure à la main

La console et les clics

Un serveur créé en vingt clics, un groupe de sécurité modifié « juste pour tester », une règle oubliée.

Personne ne sait reproduire l'environnement de production. Le document d'installation a trois versions de retard.

La dérive

Staging et production divergent lentement. Un correctif marche ici, pas là.

Un départ dans l'équipe, et le savoir part avec. Un incident, et l'on reconstruit de mémoire.

Le serveur configuré à la main est un animal de compagnie : unique, soigné, irremplaçable. On veut du bétail : numéroté, remplaçable, recréé à l'identique en une commande.

Demander qui a déjà hérité d'un serveur dont personne ne connaissait la configuration. La métaphore « pets vs cattle » est brutale mais elle marque. Point clé : le problème n'est pas la console AWS, c'est l'absence de trace et de reproductibilité.
Infrastructure as Code

Décrire, versionner, relire, appliquer

Reproductible

La même description produit la même infrastructure, aujourd'hui et dans six mois, ici et dans une autre région.

Versionnée

Dans Git, comme le reste. Qui a ouvert ce port, quand, pourquoi : git log répond.

Revue

Une pull request pour un changement d'infrastructure. Un collègue relit, la CI vérifie le plan avant d'appliquer.

Trois outils, trois rôles

Terraform
Provisionner : créer les ressources cloud (réseau, serveurs, bases).
Ansible
Configurer : installer et régler ce qui tourne sur les serveurs.
Kubernetes
Orchestrer : exécuter les conteneurs, les répliquer, les mettre à jour.
Insister sur « relire » : c'est la pratique DevOps du jour 1 appliquée à l'infrastructure. Le plan Terraform affiché dans une PR est l'équivalent du diff de code. Présenter les trois outils comme des couches, pas des concurrents.
Partie 1 / 4

Terraform

Décrire une infrastructure cloud dans des fichiers texte, et laisser l'outil calculer ce qu'il faut créer, modifier ou détruire.

Vocabulaire

Cinq mots pour tout comprendre

provider
Le greffon qui parle à une API. aws, azurerm, google, kubernetes, gitea… des centaines.
resource
Un objet à créer. Un VPC, une instance, un bucket. Identifié par un type et un nom local.
variable
Un paramètre d'entrée. La région, la taille de la machine, votre nom. Avec type et valeur par défaut.
output
Une valeur exposée après création. L'adresse IP publique, une commande SSH prête à copier.
state
La mémoire de Terraform. Ce qu'il a créé, avec quels identifiants. Sans lui, il recrée tout.

Le langage s'appelle HCL : des blocs, des attributs, des références entre ressources. Déclaratif : on décrit l'état voulu, pas les étapes.

Faire le parallèle avec un langage de programmation : provider = bibliothèque, resource = objet, variable = argument, output = valeur de retour, state = base de données. Le mot « déclaratif » reviendra avec Kubernetes cet après-midi.
Le cycle de travail

Écrire, planifier, appliquer

Le plan est un diff entre ce que décrit le code et ce que contient l'état. On le lit toujours avant d'appliquer. Le destroy est un plan qui supprime tout.

Insister sur plan : c'est la sécurité de l'outil. Un plan qui annonce « 1 to destroy » sur une base de données doit faire tiquer. Montrer en direct un init puis un plan sur le projet du jour, lire ensemble les lignes + et ~.
Un premier fichier

Un serveur en vingt lignes

terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.0" }
  }
}

provider "aws" {
  region = var.region
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.ubuntu.id
  instance_type = "t3.micro"
  key_name      = aws_key_pair.formini.key_name
  vpc_security_group_ids = [aws_security_group.web.id]
  subnet_id     = aws_subnet.public.id
  tags = { Name = "formini-${var.owner}" }
}
terraform {}
Providers requis, versions verrouillées.
provider
La région. Les identifiants viennent de l'environnement, jamais du code.
resource
Un type (aws_instance) et un nom local (web).
références
aws_subnet.public.id : l'ordre de création en découle.
Lire le fichier de haut en bas. Le point à retenir : les références entre ressources construisent un graphe de dépendances, Terraform crée dans le bon ordre et en parallèle quand c'est possible. Rappeler la règle d'hier sur les secrets : jamais dans Git.
Paramétrer et exposer

Variables en entrée, outputs en sortie

variable "region" {
  type    = string
  default = "eu-west-3"   # Paris
}

variable "owner" {
  type        = string
  description = "Votre prénom, pour les tags"
}

variable "public_key_path" {
  type    = string
  default = "~/.ssh/id_ed25519.pub"
}
output "public_ip" {
  value = aws_instance.web.public_ip
}

output "ssh" {
  value = "ssh ubuntu@${aws_instance.web.public_ip}"
}
terraform apply -var="owner=formini-a1"
# ou : fichier terraform.tfvars
terraform output public_ip

Une variable sans valeur par défaut est demandée à l'exécution. Les valeurs vont dans terraform.tfvars, exclu de Git s'il contient quoi que ce soit de sensible.

La clé publique du jour 1 est réutilisée : Terraform l'envoie à AWS comme key pair. Pas de nouvelle clé à générer. Montrer terraform output après l'apply : c'est le point d'entrée d'Ansible juste après.
L'état

Le fichier le plus précieux du projet

terraform.tfstate associe chaque ressource du code à un objet réel : identifiant d'instance, identifiant de VPC, adresses.

  • Perdu : Terraform ne connaît plus rien, et recrée tout en double.
  • Partagé par e-mail : deux personnes appliquent, l'état diverge.
  • Il contient des valeurs sensibles en clair.

En équipe : un état distant

terraform {
  backend "s3" {
    bucket       = "formini-tfstate"
    key          = "formation/formini-a1.tfstate"
    region       = "eu-west-3"
    use_lockfile = true   # verrou natif S3
  }
}

Un bucket S3 versionné, un verrou contre les applications simultanées. Jamais l'état dans Git.

Aujourd'hui l'état reste local pour la simplicité. Avant terraform destroy, vérifiez que le fichier est bien là : sans lui, le nettoyage se fait à la main dans la console.

L'état est le concept qui surprend : Terraform ne « regarde » pas AWS pour savoir ce qu'il a créé, il lit son fichier (puis le rafraîchit). Anecdote utile : un tfstate commité dans Git public expose des mots de passe de base de données. Le backend S3 est la bonne pratique, mentionnée, pas pratiquée aujourd'hui.

Un réseau, un serveur, une clé

Neuf ressources

Les commandes

Sept commandes, dont une obligatoire

Partie 2 / 4

Ansible

Le serveur existe. Il faut maintenant y installer Docker et lancer l'application, sans jamais s'y connecter à la main.

Principe

Configurer des serveurs sans agent

Ansible se connecte en SSH depuis votre poste, exécute des petits modules Python sur la cible, et repart. Rien à installer côté serveur.

  • La clé SSH du jour 1 suffit : Ansible l'utilise.
  • Tout est en YAML, lisible par un non-développeur.
  • Idempotent : rejouer un playbook sur un serveur déjà configuré ne change rien.
inventaire
La liste des machines, par groupe. [web], [db].
module
Une action élémentaire : apt, copy, service, user.
tâche
Un appel de module, avec un nom lisible.
playbook
Des tâches ordonnées, appliquées à un groupe.
rôle
Un playbook réutilisable, emballé avec ses fichiers.
Comparer avec un script shell : le script dit « fais ceci », Ansible dit « assure-toi que ceci est vrai ». Le mot idempotent est le plus important de la partie : un apt install déjà fait est ignoré, un fichier identique n'est pas recopié. Lien direct avec la clé SSH créée au jour 1.
Inventaire et commandes ad hoc

Parler à dix serveurs comme à un seul

[web]
15.188.42.17  ansible_user=ubuntu

[web:vars]
ansible_ssh_private_key_file=~/.ssh/id_ed25519
ansible_python_interpreter=/usr/bin/python3
[defaults]
inventory = inventory.ini
host_key_checking = False
# la cible répond-elle ?
ansible web -m ping

# une commande sur tout le groupe
ansible web -a "uptime"

# un module, avec élévation de droits
ansible web -b -m apt -a "name=htop state=present"

# collecter les faits (OS, IP, CPU…)
ansible web -m setup | head -40

L'IP vient de terraform output. Les commandes ad hoc servent au diagnostic ; pour configurer, on écrit un playbook.

Démo : ping puis uptime sur l'instance créée tout à l'heure. Montrer la sortie verte « SUCCESS » et le JSON. host_key_checking à False est acceptable en formation, pas en production. Les faits sont des variables disponibles dans les playbooks.
Playbook

Anatomie d'un playbook

- name: Préparer le serveur Formini Tasks
  hosts: web
  become: true
  tasks:
    - name: Installer Docker
      ansible.builtin.apt:
        name: [docker-ce, docker-compose-plugin]
        state: present
        update_cache: true
      notify: Redémarrer Docker
    - name: Copier l'application
      ansible.builtin.copy:
        src: ../app/
        dest: /opt/formini-tasks/
  handlers:
    - name: Redémarrer Docker
      ansible.builtin.service:
        name: docker
        state: restarted
hosts
Le groupe d'inventaire ciblé.
become
Passer root (sudo).
state
L'état voulu, pas l'action.
notify
Un handler, joué une fois à la fin, seulement si quelque chose a changé.
ansible-playbook playbook.yml
ansible-playbook playbook.yml --check   # simulation
ansible-playbook playbook.yml -t docker # par tag
Lire les tâches comme des phrases. Lancer le playbook deux fois en démo : la première sortie est jaune (changed), la seconde verte (ok) : c'est l'idempotence visible. Le handler ne se déclenche que si quelque chose a changé.

Partie 3 / 4

Kubernetes

Pods, Deployments et Services : faire tourner des conteneurs sur plusieurs machines comme s'il n'y en avait qu'une.

Pourquoi

Docker Compose s'arrête à une machine

Un serveur tombe

Avec Compose, l'application tombe avec lui. Kubernetes relance les conteneurs ailleurs, seul.

Le trafic double

Avec Compose, on édite un fichier et on prie. Kubernetes passe de 2 à 10 exemplaires en une commande.

Une nouvelle version

Avec Compose, quelques secondes d'interruption. Kubernetes remplace les exemplaires un par un, sans coupure, et revient en arrière si ça casse.

Kubernetes est une boucle de réconciliation : on déclare l'état voulu (« 3 exemplaires de cette image »), il compare en permanence avec la réalité et corrige l'écart. Même logique que Terraform, en continu.

Revenir au compose.yaml du jour 2 : c'était parfait pour développer, insuffisant pour exploiter. Le mot « réconciliation » est la clé : faire le lien avec le plan Terraform, mais exécuté toutes les secondes par le cluster lui-même.
Architecture

Un plan de contrôle, des nœuds

Vous ne parlez qu'à l'API server, avec kubectl. Le reste est la machinerie interne. Avec kind, tout ceci tourne dans des conteneurs Docker sur votre VM.

Ne pas s'attarder : les participants n'auront pas à administrer le control plane. Retenir deux choses : kubectl envoie des objets YAML à l'API, et les controllers font le reste. kind = Kubernetes in Docker, chaque nœud est un conteneur.
Les objets

Deployment, ReplicaSet, Pod, Service

Un Pod est l'unité d'exécution : un ou plusieurs conteneurs, une IP éphémère. On ne crée jamais de Pod à la main : le Deployment s'en charge, et le Service les rend joignables par un nom.

Le Pod est mortel : il peut disparaître à tout instant, son IP change. D'où le Service, qui suit les pods par leurs labels. Le ReplicaSet est invisible au quotidien, mais c'est lui qui permet le rolling update : le Deployment crée un nouveau ReplicaSet et transfère les pods progressivement.
Le Deployment

Déclarer l'application

apiVersion: apps/v1
kind: Deployment
metadata:
  name: tasks
  namespace: formini-tasks
spec:
  replicas: 2
  selector:
    matchLabels: { app: tasks }
  template:
    metadata:
      labels: { app: tasks }
    spec:
      containers:
        - name: tasks
          image: gitea.formini.local:3000/equipe-a/formini-tasks:v1.0.0
          ports: [{ containerPort: 5000 }]
          env:
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef: { name: tasks-secret, key: POSTGRES_PASSWORD }
            - name: DATABASE_URL
              value: postgresql://formini:$(POSTGRES_PASSWORD)@postgres:5432/tasks
replicas
Combien de pods identiques.
selector
Les pods possédés : ceux qui portent ce label.
template
Le moule des pods : image, ports, variables.
namespace
Un espace isolé par application.

postgres dans l'URL est le nom du Service de la base : le DNS est fourni.

Trois niveaux de métadonnées, c'est ce qui perd les débutants : celles du Deployment, celles du template de pod, et le selector qui les relie. Montrer que les labels du template et le selector sont identiques, sinon kubectl refuse. La syntaxe $(VAR) est l'expansion de variable native de Kubernetes.
Exposer

Trois types de Service

ClusterIP

Joignable dans le cluster seulement, par son nom DNS. Le défaut. Parfait pour la base de données.

postgres:5432

NodePort

Ouvre un port (30000–32767) sur chaque nœud. Simple, pratique en local avec kind.

http://localhost:8080 → 30080

LoadBalancer

Demande un répartiteur de charge au cloud (ELB sur AWS). Une IP publique, prête pour la production.

EKS, GKE, AKS

apiVersion: v1
kind: Service
metadata: { name: tasks, namespace: formini-tasks }
spec:
  type: NodePort
  selector: { app: tasks }
  ports: [{ port: 80, targetPort: 5000, nodePort: 30080 }]
Le Service est un répartiteur de charge interne : chaque requête vers tasks:80 va vers l'un des pods, tour à tour. Avec kind on mappe le NodePort 30080 vers le port 8080 de la VM via la configuration du cluster. Mentionner Ingress comme couche HTTP au-dessus, en bonus de l'atelier.
Configuration

ConfigMap et Secret

apiVersion: v1
kind: Secret
metadata: { name: tasks-secret, namespace: formini-tasks }
type: Opaque
stringData:
  POSTGRES_PASSWORD: change-moi
# ou, sans fichier :
kubectl -n formini-tasks create secret generic tasks-secret \
  --from-literal=POSTGRES_PASSWORD='un-vrai-mot-de-passe'

secret.yaml avec un vrai mot de passe ne va pas dans Git. On commite secret.example.yaml, comme .env au jour 2.

ConfigMap
Configuration non sensible : niveau de log, URL publique, fichier de conf.
Secret
Mots de passe, jetons, clés. Encodé base64, pas chiffré par défaut.
injection
Variables d'environnement (valueFrom) ou fichiers montés dans le pod.
Même discipline qu'avec les secrets Gitea hier : la valeur vit hors du dépôt. Montrer kubectl get secret -o yaml et décoder le base64 pour casser l'illusion de chiffrement. Les outils de production (Sealed Secrets, External Secrets, Vault) ne sont pas au programme.
Santé et ressources

Dire à Kubernetes comment surveiller

readinessProbe:
  httpGet: { path: /health, port: 5000 }
  initialDelaySeconds: 5
  periodSeconds: 5
livenessProbe:
  httpGet: { path: /health, port: 5000 }
  initialDelaySeconds: 15
  periodSeconds: 10
resources:
  requests: { cpu: 100m, memory: 128Mi }
  limits:   { cpu: 500m, memory: 256Mi }

/health vérifie la base : un pod dont la base est injoignable est retiré du trafic, pas redémarré en boucle.

readiness
Prêt à servir ? Non : le Service ne lui envoie rien.
liveness
Encore vivant ? Non : le conteneur est redémarré.
requests
Ce que le scheduler réserve pour placer le pod.
limits
Le plafond. Mémoire dépassée : OOMKilled.
Sans readiness probe, le rolling update envoie du trafic à des pods qui démarrent encore : erreurs 502 pendant quelques secondes. Sans requests, le scheduler entasse tout sur un nœud. Les valeurs ici sont celles de la solution de l'atelier.

EKS
Le service géré d'AWS : control plane facturé à l'heure, nœuds EC2. Même YAML, même kubectl.
Réflexe de diagnostic à écrire au tableau : get pods → describe pod → logs. Les trois commandes résolvent 90 % des problèmes de l'atelier. Insister : le YAML écrit sur kind est celui que l'on appliquerait sur EKS, sans modification sauf le type de Service.
Partie 4 / 4

Mise à l'échelle & mises à jour progressives

Ce pour quoi on a adopté Kubernetes : plus d'exemplaires en une commande, une nouvelle version sans coupure, un retour arrière en dix secondes.

Mise à l'échelle

De deux à dix exemplaires

# manuel
kubectl scale deploy/tasks --replicas=4
kubectl get pods -w        # les nouveaux pods arrivent

# ou dans le YAML, puis
kubectl apply -f k8s/app.yaml

# automatique (HPA), avec metrics-server
kubectl autoscale deploy/tasks \
  --min=2 --max=10 --cpu-percent=70
kubectl get hpa
  • Le Service répartit aussitôt sur les nouveaux pods, dès que leur readiness répond.
  • Réduire est aussi simple : les pods en trop sont arrêtés proprement (SIGTERM, délai de grâce).
  • Le HorizontalPodAutoscaler ajuste replicas selon le CPU ou une métrique maison. Il lui faut metrics-server et des requests définies.

Mettre à l'échelle une application sans état est trivial. La base de données, elle, ne se réplique pas en changeant un chiffre : c'est un sujet à part (StatefulSet, opérateurs, service managé).

Démo : scale à 4 avec get pods -w dans un second terminal, puis générer du trafic avec un boucle curl et montrer les logs de plusieurs pods qui répondent. Préciser que la base reste à un seul exemplaire : c'est volontaire.
Mise à jour progressive

Remplacer sans couper

strategy:
  type: RollingUpdate
  rollingUpdate:
    maxSurge: 1          # pods en plus pendant la bascule
    maxUnavailable: 0    # jamais moins que replicas
kubectl set image deploy/tasks \
  tasks=gitea.formini.local:3000/equipe-a/formini-tasks:v1.1.0
kubectl rollout status deploy/tasks
kubectl rollout history deploy/tasks
Dérouler la frise de gauche à droite. maxUnavailable: 0 garantit qu'on n'a jamais moins de pods que demandé ; maxSurge: 1 autorise un pod temporaire en plus. La readiness probe est ce qui rend la bascule sûre. Montrer rollout status en direct avec une boucle curl qui ne rend jamais d'erreur.
Retour arrière

Quand la nouvelle version casse

# déployer une image qui n'existe pas
kubectl set image deploy/tasks tasks=…:v9.9.9
kubectl get pods
#  tasks-5f…  0/1  ImagePullBackOff
#  tasks-7c…  1/1  Running   ← v1.1.0 sert toujours

kubectl rollout status deploy/tasks --timeout=60s
# error: deployment "tasks" exceeded its progress deadline

kubectl rollout undo deploy/tasks
kubectl rollout undo deploy/tasks --to-revision=2
  • Kubernetes n'a pas retiré les anciens pods : la nouvelle version n'a jamais passé la readiness.
  • Le undo réactive le ReplicaSet précédent, les pods reviennent en secondes.
  • rollout history garde dix révisions par défaut. Annoter avec --record ou une annotation kubernetes.io/change-cause.

C'est la métrique DORA « temps de rétablissement » du jour 1, ramenée à une commande.

Faire la démo de la panne volontaire : image inexistante, puis une image qui démarre mais dont /health renvoie 503. Dans les deux cas le trafic n'est jamais interrompu. Boucler sur la métrique DORA pour montrer que tout s'assemble.
