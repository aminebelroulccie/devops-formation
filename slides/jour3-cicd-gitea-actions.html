Partie 1 / 4

Intégration et livraison continues

Pourquoi vérifier chaque commit, et ce qu'un pipeline doit faire entre le code et la production.

Transition d'une phrase : avant d'ouvrir un fichier YAML, on se met d'accord sur ce qu'un pipeline doit faire et pourquoi. Dix minutes de concepts, puis on passe à l'outil.
Avant

L'enfer de l'intégration

Chacun dans sa branche, pendant des semaines

Le jour de la fusion, rien ne compile. Les tests ? On les lancera après. Le build de release est un rituel de deux jours, avec un seul expert capable de le faire.

Le symptôme

« Ça marchait sur ma machine. » Personne ne sait quelle version est en production ni comment elle a été construite.

Plus on attend pour intégrer, plus la douleur est grande. La seule parade : intégrer tout le temps, et laisser une machine vérifier à chaque fois.

Raconter le vendredi de release : la branche de six semaines, les 40 conflits, le build qui ne passe que sur le poste de Karim. Demander qui a connu un build que seule une personne savait lancer. Transition : la CI, c'est rendre ce rituel ennuyeux, répétable et instantané.
Définitions

CI, CD et… CD

Intégration continue

Chaque commit est fusionné tôt et vérifié automatiquement : compilation, lint, tests. On sait en minutes si l'on a cassé quelque chose.

Livraison continue

Chaque version validée est prête à être déployée : image construite, taguée, publiée. Le déploiement reste un clic humain.

Déploiement continu

Le clic disparaît : ce qui passe le pipeline part en production tout seul. Exige des tests et une supervision solides.

Aujourd'hui : intégration continue le matin, livraison continue l'après-midi. Le déploiement continu arrive demain avec Kubernetes.

Les deux « CD » sont souvent confondus. La différence tient en une question : qui appuie sur le bouton ? Livraison continue = l'humain décide quand ; déploiement continu = le pipeline décide. Rares sont les équipes qui ont besoin du déploiement continu dès le départ.
Pourquoi

Deux idées simples

10 min

Un retour rapide

Un bug trouvé dix minutes après le commit se corrige en dix minutes : le contexte est encore dans la tête. Le même bug trouvé trois semaines plus tard coûte une journée.

1

Petits lots

Un commit de vingt lignes qui casse le pipeline se diagnostique d'un coup d'œil. Une fusion de deux mille lignes, non. La CI pousse naturellement vers des changements petits et fréquents.

Règle d'équipe : un pipeline rouge sur main est la priorité absolue. On ne pousse rien d'autre tant qu'il n'est pas vert.

Dix minutes est la cible classique pour la durée totale d'un pipeline de CI. Au-delà, les gens arrêtent d'attendre et empilent les commits. Relier aux métriques DORA du jour 1 : délai de livraison et taux d'échec dépendent directement de la vitesse du retour.
Les étapes

L'anatomie d'un pipeline

Chaque étape ne s'exécute que si la précédente a réussi. Les plus rapides d'abord : un lint en dix secondes évite d'attendre un build de trois minutes pour rien.

Parcourir les six étapes de gauche à droite. Souligner l'ordre : les vérifications les moins chères en premier. La publication ne se fait que sur main, pas sur les pull requests, pour ne pas remplir le registre d'images de brouillon. Le déploiement en pointillé est pour demain.
Ce que vérifie chaque étape

Des questions, pas des outils

ÉtapeLa questionOutil chez nousDurée visée
LintLe code respecte-t-il les règles de l'équipe ?flake810 s
TestsLe comportement attendu est-il préservé ?pytest1 min
BuildPeut-on produire un artefact identique à chaque fois ?docker build2 min
ScanL'artefact embarque-t-il des failles connues ?trivy30 s
PublicationL'artefact est-il retrouvable, versionné, immuable ?registre Gitea30 s

Les outils changent d'un projet à l'autre, les questions restent les mêmes. Un pipeline Java remplace flake8 par Checkstyle et pytest par JUnit ; la structure ne bouge pas.

Le but de cette diapo est de détacher la notion d'étape des outils. Demander à la salle : dans vos projets, qui répond à la question « est-ce que l'artefact est retrouvable » ? Souvent personne. Noter les durées : elles donnent la cible des dix minutes.
Partie 2 / 4

Gitea Actions

Un fichier YAML dans le dépôt, un runner qui écoute : le moteur de CI/CD intégré à notre forge.

On entre dans l'outil. Prévenir : la syntaxe est celle de GitHub Actions, donc tout ce qu'ils ont pu voir ailleurs s'applique. Les diapos qui suivent préparent directement l'atelier de 10:45.
Anatomie d'un workflow

Un fichier YAML dans le dépôt

name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Dépendances
        run: |
          python3 -m venv .venv
          .venv/bin/pip install -q -r requirements-dev.txt
      - name: Lint
        run: .venv/bin/flake8 .
      - name: Tests
        run: .venv/bin/pytest -q
on
Quand : push, pull request, tag, horaire.
jobs
Quoi : des unités indépendantes, en parallèle par défaut.
runs-on
Où : l'étiquette du runner qui prendra le job.
steps
Comment : commandes ou actions, dans l'ordre.

Fichier dans .gitea/workflows/. Même syntaxe que GitHub Actions : les exemples se transposent tels quels.

Lire le fichier de haut en bas avec la salle. Quatre questions : quand, quoi, où, comment. Insister sur le fait que le workflow est versionné avec le code : il évolue dans les mêmes pull requests, et il est relu comme le reste.
Le vocabulaire

Les mots-clés qui reviennent partout

uses
Appelle une action réutilisable : actions/checkout@v4 récupère le code.
run
Exécute une commande shell. Multi-ligne avec |.
needs
Ordonne les jobs : build attend que test soit vert.
if
Condition : gitea.event_name == 'push'.
env
Variables d'environnement, au niveau workflow, job ou step.
secrets
Valeurs chiffrées côté Gitea : ${{ secrets.REGISTRY_TOKEN }}.
matrix
Exécute le même job avec plusieurs valeurs : versions de Python, systèmes.
artifacts
Fichiers conservés après le job : rapport de tests, binaire.

Le contexte ${{ gitea.sha }}, ${{ gitea.ref_name }}, ${{ gitea.event_name }} décrit l'événement en cours. github.* fonctionne aussi, par compatibilité.

Ne pas tout détailler : cette diapo sert de référence, on y reviendra pendant l'atelier. Retenir surtout needs, if et secrets, qui seront utilisés cet après-midi. Mentionner que les expressions entre doubles accolades sont évaluées par Gitea avant l'exécution.
Sous le capot

Gitea et act_runner

Le runner interroge Gitea, jamais l'inverse : il peut tourner derrière un pare-feu, sans port ouvert. Un seul Gitea, autant de runners que l'on veut.

Le point à faire passer : Gitea ne fait qu'orchestrer, c'est le runner qui travaille. Le runner tourne sur votre VM, donc quand un job est lent, c'est votre VM qui est lente. Avantage du polling : pas d'ouverture réseau entrante, le runner peut être n'importe où.
act_runner

Étiquettes : où tourne un job

Chaque runner annonce des étiquettes. Un job demande une étiquette avec runs-on. Gitea les apparie.

ÉtiquetteModeLe job tourne…
ubuntu-latest:hosthostdirectement sur la VM, avec ses outils
ubuntu-latest:docker://node:20dockerdans un conteneur jetable

Mode host (notre choix)

  • Docker, Python, trivy déjà là : pas d'installation à chaque job.
  • Rapide, simple à déboguer : on peut rejouer les commandes à la main.
  • Moins isolé : un job peut salir la machine.

Mode docker

  • Environnement propre et reproductible à chaque job.
  • Construire une image depuis un conteneur demande du Docker-dans-Docker.
En formation, on choisit le mode host pour aller vite et voir ce qui se passe. En production, le mode docker est la norme pour l'isolation. Mentionner qu'une étiquette peut aussi cibler un système (windows, arm) ou une capacité (gpu).
Enregistrement

Brancher un runner sur Gitea

# 1. jeton : Gitea → Administration → Actions → Runners
# 2. enregistrer le runner avec son étiquette
act_runner register --no-interactive \
  --instance http://gitea.formini.local:3000 \
  --token <JETON> \
  --name vm-amina \
  --labels ubuntu-latest:host

# 3. le lancer comme service
sudo systemctl enable --now act_runner
journalctl -u act_runner -f
instance
L'URL de Gitea, celle que vous utilisez dans le navigateur.
token
Jeton d'enregistrement, global, par organisation ou par dépôt.
labels
Ce que ce runner sait faire. Doit correspondre à runs-on.

Vérifier : Dépôt → Paramètres → Actions → Runners. Un point vert, sinon le job restera « en attente » pour toujours.

Les runners sont déjà enregistrés sur les VM par le script de préparation. Montrer dans l'admin Gitea la liste des runners et leurs étiquettes : c'est le premier endroit où regarder quand un job ne démarre pas. Un job en attente sans runner libre reste en attente indéfiniment.
Lire un run

Où regarder quand c'est rouge

  1. L'onglet Actions du dépôt liste les runs par workflow, avec le commit et la branche qui les ont déclenchés.
  2. Le job en échec est marqué d'une croix. Un clic ouvre les steps ; seul le step fautif est déplié.
  3. La dernière ligne du journal dit presque toujours pourquoi. Remonter de là, pas depuis le début.
  4. Rejouer en local la commande exacte du step sur la VM : même outil, même dossier, même résultat.

Un job en attente et non en échec n'est pas un bug du code : c'est un runner absent ou une étiquette qui ne correspond pas.

Montrer un run réel dans l'interface : navigation, dépliage des steps, recherche dans le journal. Faire la distinction entre les trois états : en attente, en cours, terminé. Le piège classique du matin sera le job en attente parce que le runner est tombé.

Secrets et sécurité

Comment un pipeline manipule des mots de passe sans jamais les montrer, et ce qu'il vérifie avant de livrer.

Reprise après le déjeuner. Demander qui a encore un run rouge non compris : le régler devant tout le monde en deux minutes avant de continuer. Puis annoncer : secrets, scan, protection de branche.
Les secrets

Jamais dans le code. Jamais.

Ce qui est un secret

  • Jetons d'accès au registre, à l'API, au cloud.
  • Mots de passe de base de données.
  • Clés SSH privées, certificats.

Ce qui arrive sinon

Un secret commité est dans l'historique pour toujours, même après suppression. Sur une forge publique, il est exploité en quelques minutes.

.env
En local seulement, et dans .gitignore dès le premier commit.
Gitea
Secrets chiffrés, définis par dépôt ou par organisation, jamais relisibles.
Journaux
Gitea masque la valeur par *** si elle apparaît dans une sortie.
Rotation
Un secret exposé se révoque et se remplace, il ne se « cache » pas.
Histoire vraie à raconter : clés AWS poussées sur GitHub, facture de plusieurs milliers d'euros le lendemain matin, des robots scannent les commits en continu. Insister sur « pour toujours » : git rm ne suffit pas, il faut réécrire l'historique et surtout révoquer le secret.
Secrets dans Gitea

Déclarer, puis utiliser

env:
  REGISTRY: gitea.formini.local:3000

steps:
  - name: Connexion au registre
    run: |
      echo "${{ secrets.REGISTRY_TOKEN }}" \
        | docker login $REGISTRY \
            -u "${{ secrets.REGISTRY_USER }}" \
            --password-stdin
  1. Créer un jetonProfil → Paramètres → Applications, droit package : write.
  2. Déclarer les secretsDépôt → Paramètres → Actions → Secrets : REGISTRY_USER, REGISTRY_TOKEN.
  3. Lire avec ${{ secrets.NOM }}La valeur n'apparaît jamais dans l'interface ni les logs.

--password-stdin garde le jeton hors de la liste des processus.

Démo : créer le jeton, le déclarer, lancer un run qui l'affiche avec echo pour montrer les astérisques. Puis supprimer ce step : on ne laisse pas traîner un echo de secret, même masqué. Un secret d'organisation est partagé par tous les dépôts de l'équipe, pratique pour le registre.
Analyse

Trois filets de sécurité

Qualité du code

flake8 attrape les erreurs bêtes : variable inutilisée, import manquant, code mort. Dix secondes, zéro faux positif grave.

Dépendances

pip-audit compare requirements.txt aux bases de vulnérabilités connues. La faille vient rarement de votre code, souvent d'une bibliothèque.

Image

trivy analyse l'image Docker entière : système de base, paquets, bibliothèques Python. Il bloque le pipeline si une faille critique est corrigeable.

L'analyse n'est utile que si elle bloque. Un rapport que personne ne lit ne protège de rien : --exit-code 1 fait du scan une barrière, pas un avis.

Trois niveaux : le code, les dépendances, l'image. Demander quel niveau est le plus souvent oublié : l'image, parce que l'on ne pense pas à l'OS de base. Le mot-clé est bloquer : le scan doit avoir un pouvoir de veto sur la publication.
Trivy

Scanner une image en pratique

# vue d'ensemble, lecture humaine
trivy image gitea.formini.local:3000/equipe-a/formini-tasks:a1b2c3d

# dans le pipeline : ne bloquer que sur du critique corrigeable
trivy image \
  --severity CRITICAL \
  --ignore-unfixed \
  --exit-code 1 \
  gitea.formini.local:3000/equipe-a/formini-tasks:a1b2c3d
severity
Niveaux retenus : CRITICAL d'abord, HIGH plus tard.
ignore-unfixed
Ignore les failles sans correctif disponible.
exit-code
Non nul si faille trouvée : le step échoue.

Remède courant : reconstruire sur une image de base à jour.

Démo sur l'image d'hier : montrer le tableau de trivy, le nombre de failles par sévérité, puis la commande bloquante. Expliquer ignore-unfixed : sans elle, le pipeline serait rouge en permanence à cause de failles du système de base sans correctif disponible.
Protection de branche

Le pipeline, gardien de main

  1. Dépôt → Paramètres → Branches, protéger main.
  2. Interdire le push direct, exiger une approbation.
  3. Exiger le statut test : la fusion attend le pipeline.

Combiné à la revue d'hier : un humain et une machine valident chaque changement.

Montrer les deux PR côte à côte. Le bouton de fusion grisé est la matérialisation de tout le cours : personne ne peut contourner les tests, pas même l'admin. Faire la manipulation en direct dans les paramètres de branche, et noter le nom exact du statut : CI / test (pull_request), d'où le motif CI / test*.
Partie 4 / 4

Stratégies de livraison

Nommer les versions, publier au bon moment, séparer les environnements.

Dernière partie théorique, courte. Le but est de donner le vocabulaire des étiquettes et des environnements avant le défi, qui demande de publier une image versionnée.
Nommer les images

Une étiquette dit d'où vient l'image

ÉtiquetteExempleProduit parSert à
SHA court:a1b2c3dchaque push sur mainretrouver le commit exact, déployer en test
Semver:v1.4.2un tag Git v*versions livrées, changelog, retour arrière
latest:latestle dernier build de mainconfort local. Jamais en production.

Immuable

Une étiquette, une image, pour toujours. On ne « réécrit » jamais v1.4.2 : on publie v1.4.3.

Traçable

Du conteneur en production au commit : docker inspect → étiquette → git show a1b2c3d.

Le piège de latest : deux machines qui tirent latest à une heure d'intervalle n'ont pas la même image, et personne ne le sait. Semver : majeur.mineur.correctif, incrémenté selon la nature du changement. Demain, Kubernetes déploiera toujours une étiquette précise.
Publier sur un tag

Un workflow pour les versions

name: Release
on:
  push:
    tags: ['v*']

jobs:
  release:
    runs-on: ubuntu-latest
    env:
      REGISTRY: gitea.formini.local:3000
      IMAGE: gitea.formini.local:3000/equipe-a/formini-tasks
      VERSION: ${{ gitea.ref_name }}
    steps:
      - uses: actions/checkout@v4
      - run: docker build -t $IMAGE:$VERSION .
      - run: trivy image --severity CRITICAL --ignore-unfixed
             --exit-code 1 $IMAGE:$VERSION
      - run: echo "${{ secrets.REGISTRY_TOKEN }}" | docker login
             $REGISTRY -u "${{ secrets.REGISTRY_USER }}" --password-stdin
      - run: docker push $IMAGE:$VERSION
git tag -a v1.0.0 -m "Première version"
git push origin v1.0.0
tags: v*
Ne se déclenche que sur un tag qui commence par v.
ref_name
Le nom du tag devient l'étiquette de l'image.

Le tag est posé par un humain : c'est la décision de livrer.

Un workflow par intention : ci.yml vérifie, release.yml livre. Montrer qu'un tag est un commit nommé, immuable. Le geste de livrer tient en deux commandes, et l'image versionnée est dans le registre deux minutes plus tard.
Environnements

La même image, du test à la production

Pull requestlint, tests. Rien n'est publié.
mainimage :sha publiée. Déployée en test.
Tag v*image :vX.Y.Z. Déployée en préproduction.
Productionla même image :vX.Y.Z, promue, pas reconstruite.

Construire une fois, déployer partout

Ce qui change entre les environnements, c'est la configuration (variables, secrets), jamais l'image. Ce qui a été testé est exactement ce qui est livré.

Promotion

Passer en production n'est pas un build : c'est pointer l'environnement sur une étiquette déjà validée. Revenir en arrière, c'est pointer sur la précédente.

Principe « build once, deploy many ». Relier à la configuration par variables d'environnement vue hier avec Compose : DATABASE_URL change, l'image ne change pas. Demain avec Kubernetes, le retour arrière consistera littéralement à remettre l'étiquette précédente.
Bonnes pratiques

Un pipeline que l'équipe aime

  • Rapide : moins de dix minutes, étapes légères d'abord, jobs indépendants en parallèle.
  • Déterministe : versions épinglées dans requirements.txt, image de base taguée, pas de « dernière version » implicite.
  • Lisible : un nom par step, un job par responsabilité, un workflow par intention.
  • Reproductible localement : chaque step est une commande que l'on peut taper sur sa machine.
  • Cache : réutiliser les dépendances d'un run à l'autre (actions/cache, couches Docker).
  • Matrix : tester plusieurs versions de Python en un seul job déclaré.

Le pipeline est du code : il se relit en pull request, se refactorise, et se documente. Un README qui explique comment livrer est aussi important que le code livré.

Diapo de synthèse avant le défi. Demander à la salle quelle pratique leur manque le plus dans leurs projets actuels. Prévenir : le défi demande d'enchaîner build, scan et publication ; viser d'abord un pipeline qui marche, optimiser ensuite.
Défi en autonomie · 14:00 – 15:30 · par équipe

Build, scan et publication automatiques

  1. Secrets : jeton package : write déclaré en REGISTRY_USER / REGISTRY_TOKEN.
  2. Job build après test, sur push main seulement : image taguée avec le SHA court.
  3. Steps scan (trivy, bloquant sur CRITICAL) et publish : :sha et :latest.
  4. Protéger main : statut test requis, une approbation, pas de push direct.
  5. Livrer v1.0.0 avec release.yml : l'image versionnée apparaît dans Paquets.
