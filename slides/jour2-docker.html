Partie 1 / 4

Conteneurs et machines virtuelles

Ce qu'un conteneur isole, ce qu'il partage, et pourquoi il démarre en une seconde.

Le problème

« Ça marche sur ma machine »

Une application dépend de bien plus que son code :

  • Une version précise de Python, de bibliothèques, de pilotes.
  • Des fichiers de configuration, des variables, des chemins.
  • Un système d'exploitation avec ses paquets.

Chaque environnement, poste, test, production, dérive un peu. Les écarts se découvrent le jour du déploiement.

L'idée du conteneur : livrer l'application avec son environnement, dans un paquet unique, immuable, qui s'exécute à l'identique partout.

Analogie : le conteneur maritime. Le contenu n'intéresse pas le port ; seule la forme standard compte, et la même grue charge tout.

Demander qui a déjà passé une journée à faire tourner un projet récupéré d'un collègue. Le conteneur ne supprime pas la complexité, il la fige dans une image que tout le monde partage. Lancer la métaphore du conteneur maritime, on y reviendra pour le registre.
Comparaison

Machine virtuelle ou conteneur

Point clé : un conteneur n'a pas de noyau. C'est un processus Linux ordinaire, isolé. D'où le démarrage instantané et la taille réduite. Contrepartie : l'isolation est moins forte qu'une VM, et un conteneur Linux a besoin d'un noyau Linux (sur Windows et macOS, Docker Desktop lance une petite VM).
Sous le capot

Un processus isolé, rien de plus

namespaces
Ce que le processus voit. Son propre arbre de processus (PID 1), ses interfaces réseau, ses points de montage, son nom d'hôte, ses utilisateurs.
cgroups
Ce que le processus peut consommer. Limites de CPU, de mémoire, d'entrées-sorties. docker run --memory 256m.
overlayfs
Ce qu'il lit et écrit. Les couches de l'image en lecture seule, plus une fine couche d'écriture jetée à la suppression.
capabilities
Ce qu'il a le droit de faire. Un sous-ensemble des privilèges root, réduit par défaut.
docker run -d --name demo nginx:1.27-alpine
ps -ef | grep nginx          # visible depuis l'hôte comme un processus normal
docker exec demo ps -ef      # dans le conteneur : nginx est PID 1
Démo en direct : lancer nginx, montrer ps depuis l'hôte, puis depuis le conteneur. Le même processus, deux points de vue. Cela explique pourquoi les journaux, la mémoire et les ports se gèrent avec les outils Linux d'hier.
Partie 2 / 4

Images, conteneurs et registres

Le vocabulaire, le cycle de vie, et les commandes que l'on tape dix fois par jour.

Vocabulaire

Trois objets, un flux

DockerfileLa recette : texte, versionné dans Git
ImageLe paquet : couches immuables, taguées
ConteneurL'instance : un processus vivant
RegistreLa bibliothèque : partage des images
build
Dockerfile → image
run
image → conteneur
push / pull
image ↔ registre

Une image est à un conteneur ce qu'une classe est à un objet, ou un fichier ISO à une machine qui tourne : on peut lancer cent conteneurs depuis la même image.

Un registre public : Docker Hub. Un registre privé : celui de Gitea, aujourd'hui.

Faire répéter le vocabulaire : on construit une image, on lance un conteneur, on pousse dans un registre. L'erreur courante est de confondre image et conteneur ; la commande docker ps -a contre docker images aide à fixer la distinction.
Cycle de vie

Lancer, observer, entrer, arrêter

docker run -d --name web -p 8080:80 nginx:1.27-alpine
docker ps                      # conteneurs en marche
docker ps -a                   # y compris arrêtés
docker logs -f web             # journaux (Ctrl-C pour sortir)
docker exec -it web sh         # un shell à l'intérieur
docker stop web                # SIGTERM, puis SIGKILL après 10 s
docker start web
docker rm -f web               # supprimer (force l'arrêt)
-d
Détaché : rend la main, le conteneur continue.
-p 8080:80
Port hôte 8080 → port conteneur 80.
--name
Un nom lisible plutôt qu'un identifiant.
-it
Terminal interactif, pour exec ou run.
--rm
Supprime le conteneur à l'arrêt. Pour les essais.
Dérouler la séquence en direct, ouvrir http://localhost:8080 dans le navigateur de la VM. Montrer docker exec pour lire un fichier de config dans le conteneur. Insister : un conteneur arrêté existe encore, docker ps -a le montre, docker rm le supprime.
Persistance

Jetable, mais pas ses données

La couche d'écriture disparaît avec le conteneur. Tout ce qui doit survivre vit à l'extérieur :

volume
Géré par Docker, nommé, portable. Le choix par défaut pour les bases.
bind mount
Un dossier de l'hôte monté dans le conteneur. Code en développement, configuration.
tmpfs
En mémoire, jamais sur disque. Secrets, caches.
# volume nommé
docker volume create pgdata
docker run -d --name db \
  -e POSTGRES_PASSWORD=formini \
  -v pgdata:/var/lib/postgresql/data \
  postgres:16-alpine

# bind mount (dossier courant → /app)
docker run --rm -v "$PWD":/app -w /app python:3.12-slim \
  python -c "print('bonjour')"

docker volume ls
docker volume inspect pgdata
Démo qui marque : lancer postgres sans volume, créer une table, docker rm, relancer, la table a disparu. Puis la même chose avec le volume. Le défi de l'après-midi repose sur ce volume nommé.
Réseau

Les conteneurs se parlent par leur nom

docker network create formini
docker run -d --name db --network formini \
  -e POSTGRES_PASSWORD=formini postgres:16-alpine
docker run --rm -it --network formini postgres:16-alpine \
  psql -h db -U postgres        # « db » est résolu par le DNS Docker

docker network ls
docker network inspect formini
docker port web                 # publications de ports
  • Sur un même réseau défini par l'utilisateur, chaque conteneur est joignable par son nom.
  • Le réseau bridge par défaut ne fournit pas ce DNS : toujours créer le sien.
  • Seuls les ports publiés (-p) sont visibles depuis l'hôte.

Compose crée ce réseau pour vous ; c'est pour cela que db fonctionne comme nom d'hôte dans DATABASE_URL.

Anticiper Compose : expliquer maintenant pourquoi la chaîne de connexion de l'après-midi contiendra « db » et non « localhost ». Erreur numéro un du défi : mettre localhost dans DATABASE_URL, qui désigne le conteneur web lui-même.
Dockerfile

La recette d'une image

FROM python:3.12-slim
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
EXPOSE 5000
CMD ["gunicorn", "-b", "0.0.0.0:5000", "app:create_app()"]
docker build -t formini-tasks:0.1 .
docker run -d -p 5000:5000 formini-tasks:0.1
curl localhost:5000/health
FROM
L'image de départ. Toujours une version précise.
WORKDIR
Le dossier courant pour les instructions suivantes.
COPY
Fichiers du contexte de build → image.
RUN
Une commande exécutée au build, crée une couche.
CMD
La commande lancée au run. Une seule.

Cette version fonctionne. L'après-midi, on verra pourquoi elle est lente à reconstruire, lourde, et lancée en root.

C'est le Dockerfile que les participants écrivent dans l'atelier guidé. Volontairement naïf : l'après-midi on l'améliore ligne par ligne. Bien distinguer RUN (au build) et CMD (au run), confusion très fréquente.

Partie 3 / 4

Écrire des Dockerfiles efficaces

Rapides à reconstruire, petits, sûrs, et prêts pour un pipeline.

Couches et cache

L'ordre des instructions change tout

Chaque instruction produit une couche. Docker réutilise une couche tant que l'instruction et les fichiers qu'elle touche n'ont pas changé. Dès qu'une couche est invalidée, toutes les suivantes le sont.

Règle : du plus stable au plus volatil. Système, puis dépendances, puis code.

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
Démo chronométrée : modifier app.py, rebuild avec le Dockerfile naïf (pip tourne), puis avec la version ordonnée (deux secondes). C'est la différence entre un pipeline de 5 minutes et de 30 secondes demain.
Contexte de build

Ne copiez pas ce qui n'a rien à faire là

.git
.venv
__pycache__
*.pyc
*.db
.env
tests/
.pytest_cache
ateliers/
*.md
  • docker build . envoie tout le dossier au moteur avant la première instruction.
  • Un .venv ou un .git copié : image énorme, cache cassé à chaque commit.
  • Un .env copié : un secret dans l'image, lisible par quiconque la télécharge.

Vérifiez ce qui est dans l'image : docker run --rm image ls -la /app.

Montrer la ligne « transferring context » au début d'un build avec et sans .dockerignore. Le point sécurité sur .env prépare le jour 3 : les secrets ne vont ni dans Git ni dans l'image, ils arrivent à l'exécution.
Taille et surface d'attaque

Plus petite, plus vite, plus sûre

Image de baseTailleUsage
python:3.12≈ 1 GoCompilation, debug
python:3.12-slim≈ 150 MoNotre choix
python:3.12-alpine≈ 50 MoAttention aux roues binaires
distroless≈ 50 MoSans shell, production

Moins de paquets : moins de failles à corriger, moins d'octets à transférer, démarrage plus rapide sur Kubernetes.

# étape 1 : construire les dépendances
FROM python:3.12-slim AS build
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install \
    -r requirements.txt

# étape 2 : image finale, sans pip ni outils de build
FROM python:3.12-slim
COPY --from=build /install /usr/local
WORKDIR /app
COPY app.py .
COPY static/ static/
Le multi-stage sert surtout aux langages compilés (Go, Java) où l'image finale ne contient que le binaire. Quatre Dockerfiles commentés (Go, Python, React, Rust) sont dans ateliers/jour2-docker/exemples/ : démo optionnelle avec build-all.sh si on a de l'avance. Pour Python, le gain est modeste ; c'est le bonus du défi, on compare les tailles avec docker images.
Sécurité et exploitation

Le Dockerfile que l'on garde

FROM python:3.12-slim
ENV PYTHONDONTWRITEBYTECODE=1 PYTHONUNBUFFERED=1
WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app.py .
COPY static/ static/

RUN useradd --create-home --uid 1000 app \
 && chown -R app:app /app
USER app

EXPOSE 5000
HEALTHCHECK --interval=15s --timeout=3s --start-period=10s --retries=3 \
  CMD python -c "import urllib.request;urllib.request.urlopen('http://127.0.0.1:5000/health')"
CMD ["gunicorn", "-b", "0.0.0.0:5000", "--workers", "2", "app:create_app()"]
  • USER : jamais root en production. Une faille de l'app ne donne pas root sur l'hôte.
  • HEALTHCHECK : Docker et Compose savent si l'app est vraiment prête.
  • ENV : journaux non tamponnés, visibles aussitôt dans docker logs.
  • CMD exec : gunicorn est PID 1 et reçoit SIGTERM proprement.
C'est la solution de référence (ateliers/jour2-docker/solution/Dockerfile). Expliquer chaque ligne ajoutée par rapport au matin. La forme exec de CMD évite un shell intermédiaire qui avalerait SIGTERM : sinon docker stop attend 10 secondes puis tue.
Tags

Un tag dit quoi, jamais latest

docker build \
  -t formini-tasks:1.2.0 \
  -t formini-tasks:$(git rev-parse --short HEAD) \
  .
docker images formini-tasks
docker history formini-tasks:1.2.0
docker inspect formini-tasks:1.2.0 | grep -i user
1.2.0
Version sémantique : lisible, pour les humains et les changelogs.
a1b2c3d
SHA du commit : immuable, trace exacte du code. Le pipeline de demain l'utilisera.
latest
Un alias mouvant. Interdit en production : on ne sait jamais ce qui tourne.

Un tag est une étiquette sur une image ; plusieurs tags peuvent pointer la même image, sans la dupliquer.

Anecdote : deux serveurs avec « latest » qui tournent deux versions différentes parce que tirées à des jours différents. Le SHA de commit comme tag relie l'image au code : indispensable pour le retour arrière de Kubernetes au jour 4.
Partie 4 / 4

Docker Compose et le registre

Décrire plusieurs conteneurs dans un fichier, puis partager l'image avec l'équipe et le pipeline.

Compose

Plusieurs conteneurs, un seul fichier

Une application réelle, c'est l'app et sa base, son cache, son proxy. Les lancer à la main avec dix options chacun n'est pas reproductible.

Compose décrit l'ensemble dans compose.yaml, versionné avec le code, et le pilote en une commande.

docker compose up -d --build
docker compose ps
docker compose logs -f web
docker compose exec db psql -U formini tasks
docker compose down          # garde les volumes
docker compose down -v       # supprime aussi les données
Topologie du défi : deux services sur un réseau privé, un seul port publié, un volume pour la base. Montrer que compose down conserve pgdata et que down -v l'efface : c'est le piège classique quand on veut « repartir de zéro » sans perdre ses données.
compose.yaml · 1/2

Le service web

services:
  web:
    build: .
    image: formini-tasks:dev
    ports: ["8000:5000"]
    environment:
      DATABASE_URL: postgresql://formini:${POSTGRES_PASSWORD}@db:5432/tasks
      APP_VERSION: ${APP_VERSION:-dev}
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped
depends_on
Avec service_healthy : web attend que Postgres réponde.
${VAR}
Lue dans .env, ignoré par Git. On versionne .env.example.
restart
Relance après un crash ou un redémarrage de la VM.

Le nom d'hôte db dans l'URL est le nom du service : Compose le résout sur le réseau interne.

Sans la condition service_healthy, web démarre avant Postgres et plante avec « connection refused » : laisser les participants le constater avant de donner la solution. Montrer docker compose config, qui affiche la configuration résolue, mots de passe compris, donc à ne jamais coller dans un ticket.
compose.yaml · 2/2

Le service db et son volume

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: formini
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD}
      POSTGRES_DB: tasks
    volumes: ["pgdata:/var/lib/postgresql/data"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U formini -d tasks"]
      interval: 5s
      timeout: 3s
      retries: 10

volumes:
  pgdata:
image
Pas de build : une image officielle, version épinglée.
healthcheck
La commande qui dit « prêt ». C'est elle que depends_on attend.
volumes
Le volume nommé pgdata, déclaré en bas, survit à compose down.

Aucun port publié pour db : seule web y accède, par le réseau interne.

Faire remarquer l'absence de ports sur db : c'est une bonne pratique de sécurité, la base n'est pas exposée sur la VM. Pour y accéder on passe par docker compose exec db psql. Le healthcheck pg_isready est fourni par l'image postgres elle-même.
Registre

Publier l'image dans Gitea

# 1. s'authentifier (jeton d'accès Gitea, portée package)
docker login gitea.formini.local:3000 -u formini-a1

# 2. nommer l'image avec l'adresse du registre
docker tag formini-tasks:dev \
  gitea.formini.local:3000/equipe-a/formini-tasks:0.2.0

# 3. pousser
docker push gitea.formini.local:3000/equipe-a/formini-tasks:0.2.0

# 4. depuis une autre VM : récupérer et lancer
docker pull gitea.formini.local:3000/equipe-a/formini-tasks:0.2.0

Le nom complet d'une image dit où elle habite :

gitea.formini.local:3000 / equipe-a / formini-tasks : 0.2.0
└── registre ─────────┘   └ org ─┘   └── dépôt ──┘  └ tag
  • Sans registre dans le nom : Docker Hub par défaut.
  • Le registre Gitea est en HTTP : il est déclaré dans insecure-registries du démon (fait par le script d'installation).
  • Les images apparaissent dans Gitea → organisation → Packages.
Montrer la création du jeton dans Gitea : Settings → Applications → Generate token, portée package read/write. Le mot de passe du compte fonctionne aussi mais on prend l'habitude du jeton, celui du pipeline demain en sera un. Pousser en direct et ouvrir l'onglet Packages au projecteur.
